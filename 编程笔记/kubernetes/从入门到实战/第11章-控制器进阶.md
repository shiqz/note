## 11.1 DaemonSet

### 11.1.1 DaemonSet 核心概念

DaemonSet 是一种确保**每个 Node 上运行一个 Pod** 的控制器。当新节点加入集群时，DaemonSet 会自动在新节点上部署 Pod；当节点移除时，对应的 Pod 也会被删除。

```
┌─────────────────────────────────────────────────────────┐
│                    Kubernetes Cluster                     │
│                                                           │
│  ┌───────────────┐  ┌───────────────┐  ┌───────────────┐ │
│  │   Node-1      │  │   Node-2      │  │   Node-3      │ │
│  │  ┌──────────┐ │  │  ┌──────────┐ │  │  ┌──────────┐ │ │
│  │  │ Pod (DS) │ │  │  │ Pod (DS) │ │  │  │ Pod (DS) │ │ │
│  │  │ fluentd  │ │  │  │ fluentd  │ │  │  │ fluentd  │ │ │
│  │  └──────────┘ │  │  └──────────┘ │  │  └──────────┘ │ │
│  │  ┌──────────┐ │  │  ┌──────────┐ │  │  ┌──────────┐ │ │
│  │  │Pod(其他) │ │  │  │Pod(其他) │ │  │  │Pod(其他) │ │ │
│  │  └──────────┘ │  │  └──────────┘ │  │  └──────────┘ │ │
│  └───────────────┘  └───────────────┘  └───────────────┘ │
│                                                           │
│  DaemonSet 特点：                                          │
│  ✅ 每个 Node 上运行 1 个 Pod                              │
│  ✅ 新增 Node 自动部署 Pod                                 │
│  ✅ 节点移除时 Pod 自动删除                                │
│  ✅ 跳过已标记为 unschedulable 的节点                      │
│  ✅ 可通过 nodeSelector / nodeAffinity 控制哪些节点运行    │
└─────────────────────────────────────────────────────────┘
```

### 11.1.2 典型应用场景

| 场景 | 说明 | 示例 |
|------|------|------|
| **日志收集** | 每个节点部署日志采集 Agent | Fluentd、Fluent Bit、Logstash |
| **监控 Agent** | 每个节点采集系统指标 | Node Exporter、Datadog Agent |
| **网络插件** | 每个节点部署网络组件 | Calico、Cilium、Flannel |
| **节点存储** | 每个节点管理本地存储 | Local Volume Provisioner |
| **安全扫描** | 每个节点部署安全扫描器 | Clair、Trivy |

### 11.1.3 DaemonSet YAML 结构详解

#### 完整 YAML 配置示例

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluentd
  namespace: kube-system
  labels:
    app: fluentd
    tier: logging
  annotations:
    description: "Fluentd 日志收集 DaemonSet"

spec:
  # 标签选择器（必填，不可修改）
  selector:
    matchLabels:
      app: fluentd
      tier: logging

  # 更新策略
  updateStrategy:
    type: RollingUpdate          # 更新类型：RollingUpdate / OnDelete
    rollingUpdate:
      maxUnavailable: 1          # 最大不可用 Pod 数

  # 历史版本保留
  revisionHistoryLimit: 10

  # Pod 模板
  template:
    metadata:
      labels:
        app: fluentd
        tier: logging
      annotations:
        prometheus.io/scrape: "true"
        prometheus.io/port: "24231"

    spec:
      # ========== 节点选择 ==========
      # 方式一：nodeSelector（简单匹配）
      nodeSelector:
        kubernetes.io/os: linux
        logging-enabled: "true"

      # 方式二：nodeAffinity（复杂匹配，推荐）
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: kubernetes.io/os
                    operator: In
                    values:
                      - linux
                  - key: node-type
                    operator: In
                    values:
                      - worker
                      - general
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              preference:
                matchExpressions:
                  - key: kubernetes.io/hostname
                    operator: In
                    values:
                      - node-1
                      - node-2

      # 污点容忍（允许调度到有污点的节点）
      tolerations:
        - key: node-role.kubernetes.io/master
          operator: Exists
          effect: NoSchedule
        - key: dedicated
          operator: Equal
          value: logging
          effect: NoSchedule

      # 服务账户
      serviceAccountName: fluentd
      serviceAccount: fluentd

      # 容器定义
      containers:
        - name: fluentd
          image: fluent/fluentd:v1.16-alpine
          imagePullPolicy: IfNotPresent

          # 端口声明
          ports:
            - name: http
              containerPort: 24231
              protocol: TCP

          # 环境变量
          env:
            - name: FLUENTD_CONF
              value: "fluent.conf"
            - name: NODE_NAME
              valueFrom:
                fieldRef:
                  fieldPath: spec.nodeName

          # 资源限制
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"

          # 健康检查
          livenessProbe:
            httpGet:
              path: /health
              port: 24231
            initialDelaySeconds: 30
            periodSeconds: 30
            failureThreshold: 3

          readinessProbe:
            httpGet:
              path: /health
              port: 24231
            initialDelaySeconds: 10
            periodSeconds: 10
            failureThreshold: 3

          # 卷挂载
          volumeMounts:
            - name: varlog
              mountPath: /var/log
              readOnly: true
            - name: varlibdockercontainers
              mountPath: /var/lib/docker/containers
              readOnly: true
            - name: fluentd-config
              mountPath: /fluentd/etc
            - name: fluentd-buffer
              mountPath: /fluentd/buffer

          # 安全上下文
          securityContext:
            privileged: true
            readOnlyRootFilesystem: false

      # 卷定义
      volumes:
        - name: varlog
          hostPath:
            path: /var/log
        - name: varlibdockercontainers
          hostPath:
            path: /var/lib/docker/containers
        - name: fluentd-config
          configMap:
            name: fluentd-config
        - name: fluentd-buffer
          hostPath:
            path: /var/lib/fluentd/buffer

      # 优先级
      priorityClassName: system-node-critical
```

### 11.1.4 nodeSelector 与 nodeAffinity 对比

| 特性 | nodeSelector | nodeAffinity |
|------|-------------|-------------|
| **匹配方式** | 精确匹配（key=value） | 支持多种操作符（In, NotIn, Exists, DoesNotExist） |
| **复杂条件** | 不支持 | 支持多个条件组合（AND/OR） |
| **软/硬约束** | 仅硬约束 | 支持硬约束（required）和软约束（preferred） |
| **推荐程度** | 简单场景 | 所有场景（推荐） |

```yaml
# nodeSelector 示例
nodeSelector:
  kubernetes.io/os: linux
  logging-enabled: "true"

# nodeAffinity 示例（等效的复杂版本）
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/os
              operator: In
              values: ["linux"]
            - key: logging-enabled
              operator: In
              values: ["true"]
```

### 11.1.5 DaemonSet 管理命令

```bash
# 创建 DaemonSet
kubectl apply -f fluentd.yaml

# 查看 DaemonSet 状态
kubectl get daemonset
kubectl get daemonset -n kube-system

# 查看 DaemonSet 详情
kubectl describe daemonset fluentd -n kube-system

# 查看 DaemonSet Pod 分布
kubectl get pods -n kube-system -l app=fluentd -o wide

# 更新 DaemonSet 配置

# 查看滚动更新状态
kubectl rollout status daemonset/fluentd -n kube-system

# 回滚 DaemonSet
kubectl rollout history daemonset/fluentd -n kube-system
kubectl rollout undo daemonset/fluentd -n kube-system

# 删除 DaemonSet
kubectl delete daemonset fluentd -n kube-system

# 查看 DaemonSet YAML
kubectl get daemonset fluentd -n kube-system -o yaml
```

## 11.2 StatefulSet

### 11.2.1 StatefulSet 核心概念

StatefulSet 是为**有状态应用**设计的控制器，提供稳定的标识、有序的部署和稳定的存储。

```
┌─────────────────────────────────────────────────────────────┐
│                    StatefulSet vs Deployment                   │
│                                                               │
│  Deployment（无状态）:                                        │
│  ┌────────┐  ┌────────┐  ┌────────┐                         │
│  │ Pod-A  │  │ Pod-B  │  │ Pod-C  │  ← Pod 名称随机           │
│  │ 不稳定 │  │ 不稳定 │  │ 不稳定 │  ← Pod IP 不稳定          │
│  └────────┘  └────────┘  └────────┘                         │
│  特点：可以任意替换，不需要关心顺序                             │
│                                                               │
│  StatefulSet（有状态）:                                       │
│  ┌────────┐  ┌────────┐  ┌────────┐                         │
│  │ web-0  │  │ web-1  │  │ web-2  │  ← Pod 名称固定有序      │
│  │ 稳定  │  │ 稳定  │  │ 稳定  │  ← Pod IP 稳定              │
│  └────────┘  └────────┘  └────────┘                         │
│  特点：有序部署/删除，稳定存储绑定                             │
└─────────────────────────────────────────────────────────────┘
```

### 11.2.2 StatefulSet 三大特性

| 特性 | 说明 | 实现方式 |
|------|------|----------|
| **稳定标识** | Pod 名称有序且固定（web-0, web-1, web-2） | 基于序号的命名规则 |
| **有序部署/删除** | 按顺序逐个创建/删除 Pod | 序号控制（N-1 → 0） |
| **稳定存储** | 每个 Pod 绑定独立的持久存储 | volumeClaimTemplates |

### 11.2.3 与 Deployment 的核心区别

| 维度 | Deployment | StatefulSet |
|------|-----------|-------------|
| **Pod 名称** | 随机后缀（nginx-7d4f5b6c8-xxxxx） | 固定序号（web-0, web-1, web-2） |
| **部署顺序** | 并行创建所有 Pod | 按序号顺序创建（0 → N-1） |
| **删除顺序** | 并行删除所有 Pod | 按序号逆序删除（N-1 → 0） |
| **存储绑定** | 共享存储或无存储 | 每个 Pod 独立存储绑定 |
| **网络标识** | 不稳定 | 稳定 DNS 名称（web-0.svc-name） |
| **更新策略** | 滚动更新 | 可滚动或按序更新 |
| **适用场景** | 无状态应用 | 有状态应用（数据库、集群） |

### 11.2.4 典型应用场景

| 应用 | 说明 |
|------|------|
| **MySQL 集群** | 需要主从复制，每个实例角色固定 |
| **Redis Cluster** | 需要稳定的节点标识和数据持久化 |
| **ZooKeeper** | 需要有序的节点身份 |
| **Kafka** | 需要稳定的 Broker ID 和日志存储 |
| **etcd 集群** | 每个节点有固定的 peer URL |
| **MongoDB 副本集** | 需要稳定的节点名称 |

### 11.2.5 StatefulSet YAML 结构详解

#### 完整 YAML 配置示例（以 Redis Cluster 为例）

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: redis-cluster
  namespace: default
  labels:
    app: redis-cluster
    tier: cache
  annotations:
    description: "Redis Cluster StatefulSet"

spec:
  # Pod 数量
  replicas: 6                    # Redis Cluster 推荐 6 个节点（3主3从）

  # 标签选择器（必填，不可修改）
  selector:
    matchLabels:
      app: redis-cluster

  # 服务名称（必须匹配一个 Headless Service）
  serviceName: redis-cluster-service  # 关联的无头服务

  # 更新策略
  updateStrategy:
    type: RollingUpdate          # RollingUpdate / OnDelete
    rollingUpdate:
      partition: 0               # 从第几个 Pod 开始更新（用于灰度）

  # 历史版本保留
  revisionHistoryLimit: 10

  # Pod 模板
  template:
    metadata:
      labels:
        app: redis-cluster
      annotations:
        prometheus.io/scrape: "true"
        prometheus.io/port: "9121"

    spec:
      # 初始化容器
      initContainers:
        - name: init-redis
          image: busybox:1.36
          command:
            - sh
            - -c
            - |
              # 等待集群引导
              if [ "$HOSTNAME" = "redis-cluster-0" ]; then
                echo "Primary node, waiting for other nodes..."
              else
                echo "Secondary node, waiting for primary..."
                sleep 5
              fi

      # 容器定义
      containers:
        - name: redis
          image: redis:7.2-alpine
          command:
            - redis-server
            - --cluster-enabled
            - "yes"
            - --cluster-config-file
            - "/data/nodes.conf"
            - --cluster-node-timeout
            - "5000"
            - --appendonly
            - "yes"
            - --appendfilename
            - "appendonly.aof"
            - --dir
            - "/data"
            - --requirepass
            - "${REDIS_PASSWORD}"
          ports:
            - name: redis
              containerPort: 6379
              protocol: TCP
            - name: cluster
              containerPort: 16379
              protocol: TCP

          env:
            - name: REDIS_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: redis-secret
                  key: password
            - name: POD_IP
              valueFrom:
                fieldRef:
                  fieldPath: status.podIP
            - name: POD_NAME
              valueFrom:
                fieldRef:
                  fieldPath: metadata.name

          resources:
            requests:
              cpu: "250m"
              memory: "512Mi"
            limits:
              cpu: "1000m"
              memory: "2Gi"

          livenessProbe:
            tcpSocket:
              port: 6379
            initialDelaySeconds: 30
            periodSeconds: 10
            failureThreshold: 3

          readinessProbe:
            exec:
              command:
                - redis-cli
                - -a
                - "${REDIS_PASSWORD}"
                - ping
            initialDelaySeconds: 10
            periodSeconds: 5
            failureThreshold: 3

          volumeMounts:
            - name: redis-data
              mountPath: /data

          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: false

      # 服务账户
      serviceAccountName: redis-cluster

  # ========== 稳定存储：每个 Pod 独立的 PVC 模板 ==========
  volumeClaimTemplates:
    - metadata:
        name: redis-data
        annotations:
          description: "Redis data volume"
      spec:
        accessModes:
          - ReadWriteOnce
        storageClassName: standard
        resources:
          requests:
            storage: 10Gi
```

### 11.2.6 Headless Service（无头服务）

StatefulSet 必须配合一个 **Headless Service**（`clusterIP: None`）使用，为每个 Pod 提供稳定的 DNS 名称。

```yaml
apiVersion: v1
kind: Service
metadata:
  name: redis-cluster-service
  namespace: default
  labels:
    app: redis-cluster
spec:
  # 无头服务：不分配 ClusterIP，直接返回 Pod IP
  clusterIP: None
  selector:
    app: redis-cluster
  ports:
    - name: redis
      port: 6379
      targetPort: 6379
      protocol: TCP
    - name: cluster
      port: 16379
      targetPort: 16379
      protocol: TCP
```

**DNS 解析规则：**

```
# 每个 Pod 的 DNS 名称格式：
# <pod-name>.<service-name>.<namespace>.svc.cluster.local

# 示例：
redis-cluster-0.redis-cluster-service.default.svc.cluster.local
redis-cluster-1.redis-cluster-service.default.svc.cluster.local
redis-cluster-2.redis-cluster-service.default.svc.cluster.local

# 集群域名（所有 Pod IP）：
redis-cluster-service.default.svc.cluster.local
```

### 11.2.7 StatefulSet 管理命令

```bash

```

## 11.3 Job

### 11.3.1 Job 核心概念

Job 用于执行**一次性任务**，确保指定数量的 Pod 成功完成后结束。与 Deployment 不同，Job 关注的是"任务完成"而不是"持续运行"。

```
┌─────────────────────────────────────────────────────────┐
│                      Job 工作流程                         │
│                                                           │
│  1. 创建 Job                                              │
│     ↓                                                     │
│  2. 创建 Pod 执行任务                                     │
│     ↓                                                     │
│  3. 监控 Pod 运行状态                                     │
│     ├── Pod 成功 → 标记完成                               │
│     ├── Pod 失败 → 重新创建（取决于 backoffLimit）         │
│     └── Pod 超时 → 重新创建                               │
│     ↓                                                     │
│  4. 所有 Pod 完成 → Job 状态为 Complete                   │
│     ↓                                                     │
│  5. 成功的 Pod 保留（便于排查）                           │
│                                                           │
│  关键参数：                                               │
│  ├── completions: 需要多少个 Pod 成功完成                 │
│  ├── parallelism: 同时运行多少个 Pod                      │
│  └── backoffLimit: 失败后最多重试次数                     │
└─────────────────────────────────────────────────────────┘
```

### 11.3.2 Job YAML 结构详解

#### 完整 YAML 配置示例

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: data-migration
  namespace: default
  labels:
    app: data-migration
    tier: batch
  annotations:
    description: "一次性数据迁移任务"

spec:
  # 完成所需的 Pod 数量（默认 1）
  completions: 4

  # 并行运行的 Pod 数量（默认 1）
  parallelism: 2

  # 失败后最多重试次数（默认 6）
  backoffLimit: 3

  # 活动截止时间（超过则标记失败）
  activeDeadlineSeconds: 1800     # 30 分钟

  # TTL（完成后自动清理，Kubernetes 1.12+）
  ttlSecondsAfterFinished: 3600   # 完成后 1 小时自动删除

  # 选择器
  selector:
    matchLabels:
      app: data-migration

  # 手动选择 Pod（用于控制并行执行）
  manualSelector: false

  # Pod 模板
  template:
    metadata:
      labels:
        app: data-migration
    spec:
      # 重启策略（Job 必须是 OnFailure 或 Never）
      restartPolicy: OnFailure

      containers:
        - name: migration
          image: postgres:16-alpine
          command:
            - sh
            - -c
            - |
              echo "开始数据迁移任务..."
              echo "Pod 名称: ${POD_NAME}"
              echo "处理分片: ${JOB_COMPLETION_INDEX}"
              
              # 模拟数据迁移
              pg_dump -h ${DB_HOST} -U ${DB_USER} ${DB_NAME} | \
                psql -h ${TARGET_HOST} -U ${TARGET_USER} ${TARGET_NAME}
              
              echo "数据迁移完成"
          env:
            - name: POD_NAME
              valueFrom:
                fieldRef:
                  fieldPath: metadata.name
            - name: JOB_COMPLETION_INDEX
              valueFrom:
                fieldRef:
                  fieldPath: metadata.annotations['batch.kubernetes.io/job-completion-index']
            - name: DB_HOST
              value: "source-db.default.svc.cluster.local"
            - name: DB_USER
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: username
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: password

          resources:
            requests:
              cpu: "200m"
              memory: "256Mi"
            limits:
              cpu: "1000m"
              memory: "1Gi"

          volumeMounts:
            - name: migration-scripts
              mountPath: /scripts
            - name: temp-data
              mountPath: /tmp/data

      volumes:
        - name: migration-scripts
          configMap:
            name: migration-scripts
        - name: temp-data
          emptyDir: {}

      # 亲和性
      affinity:
        nodeAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              preference:
                matchExpressions:
                  - key: workload
                    operator: In
                    values:
                      - batch
```

### 11.3.3 Job 参数详解

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `spec.completions` | integer | 1 | 需要成功完成的 Pod 总数 |
| `spec.parallelism` | integer | 1 | 同时运行的 Pod 数量 |
| `spec.backoffLimit` | integer | 6 | 失败后最多重试次数 |
| `spec.activeDeadlineSeconds` | integer | nil | 活动截止时间（秒） |
| `spec.ttlSecondsAfterFinished` | integer | nil | 完成后自动清理时间 |
| `spec.selector` | object | - | 标签选择器 |
| `spec.manualSelector` | boolean | false | 是否手动选择 Pod |

#### completions 与 parallelism 的关系

```
场景 1：completions=1, parallelism=1
  → 顺序执行 1 个 Pod，完成即结束

场景 2：completions=3, parallelism=1
  → 顺序执行 3 个 Pod（第 1 个完成后启动第 2 个）

场景 3：completions=3, parallelism=3
  → 并行执行 3 个 Pod，全部完成即结束

场景 4：completions=1, parallelism=3
  → 同时启动 3 个 Pod，任意 1 个成功即结束（其他 Pod 被终止）

场景 5：completions=4, parallelism=2
  → 先启动 2 个 Pod，完成 1 个后补 1 个，直到 4 个完成
```

## 11.4 CronJob

### 11.4.1 CronJob 核心概念

CronJob 基于 cron 表达式**定时执行 Job**。每次调度时，CronJob 会创建一个新的 Job，由 Job 来管理 Pod 的执行。

```
┌─────────────────────────────────────────────────────────────┐
│                      CronJob 工作流程                         │
│                                                               │
│  CronJob (定时触发器)                                         │
│  │                                                            │
│  │  schedule: "0 2 * * *"  ← 每天凌晨 2 点                    │
│  │  concurrencyPolicy: Allow                                  │
│  │  successfulJobsHistoryLimit: 3                             │
│  │  failedJobsHistoryLimit: 1                                 │
│  │                                                            │
│  ├──T1──→ Job-1 → Pod-1 → 执行 → 成功 ✓                      │
│  ├──T2──→ Job-2 → Pod-2 → 执行 → 成功 ✓                      │
│  ├──T3──→ Job-3 → Pod-3 → 执行 → 失败 ✗ (保留)               │
│  └──T4──→ Job-4 → Pod-4 → 执行 → 运行中...                   │
│                                                               │
│  历史记录：                                                   │
│  ├── 成功的 Job 保留 3 个（successfulJobsHistoryLimit）       │
│  └── 失败的 Job 保留 1 个（failedJobsHistoryLimit）           │
└─────────────────────────────────────────────────────────────┘
```

### 11.4.2 schedule 语法

CronJob 的 schedule 语法与 Linux crontab 相同，由 5 个字段组成。

```
┌──────────────── 分钟 (0 - 59)
│ ┌────────────── 小时 (0 - 23)
│ │ ┌──────────── 日 (1 - 31)
│ │ │ ┌────────── 月 (1 - 12)
│ │ │ │ ┌──────── 星期 (0 - 6, 0 = 周日)
│ │ │ │ │
* * * * *   ← 每分钟执行一次
```

#### 常用时间表达式

| 表达式 | 含义 |
|--------|------|
| `* * * * *` | 每分钟 |
| `*/5 * * * *` | 每 5 分钟 |
| `0 * * * *` | 每小时整点 |
| `0 */2 * * *` | 每 2 小时 |
| `0 2 * * *` | 每天凌晨 2 点 |
| `0 2 * * 0` | 每周日凌晨 2 点 |
| `0 2 1 * *` | 每月 1 号凌晨 2 点 |
| `0 9-17 * * 1-5` | 工作日 9-17 整点 |
| `30 3 * * 1,15` | 每月 1 号和 15 号凌晨 3:30 |

### 11.4.3 concurrencyPolicy 策略

| 策略 | 说明 |
|------|------|
| **Allow** | 允许多个 Job 同时运行（默认） |
| **Forbid** | 不允许并发，跳过本次调度 |
| **Replace** | 如果上一个 Job 仍在运行，用新 Job 替换它 |

```
场景：CronJob 每 10 分钟执行一次，任务需要 15 分钟完成

Allow:   Job-1 运行中 → Job-2 启动 → 两个并发运行
Forbid:  Job-1 运行中 → Job-2 被跳过 → 仅 Job-1 运行
Replace: Job-1 运行中 → Job-1 被终止 → Job-2 替代运行
```

### 11.4.4 CronJob YAML 结构详解

#### 完整 YAML 配置示例（MySQL 备份）

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: mysql-backup
  namespace: default
  labels:
    app: mysql-backup
    tier: maintenance
  annotations:
    description: "MySQL 定时备份 CronJob"

spec:
  # 调度时间（每天凌晨 2:30 执行）
  schedule: "30 2 * * *"

  # 并发策略
  concurrencyPolicy: Forbid       # 不允许并发，避免备份冲突

  # 起始截止时间（可选）
  startingDeadlineSeconds: 300    # 错过了调度时间 5 分钟则跳过

  # 历史记录保留
  successfulJobsHistoryLimit: 3   # 保留最近 3 个成功的 Job
  failedJobsHistoryLimit: 1       # 保留最近 1 个失败的 Job

  # 暂停调度（可用于临时禁用）
  suspend: false                  # true 时暂停所有调度

  # Job 模板（与 Job spec 相同）
  jobTemplate:
    spec:
      # Job 级别的配置
      backoffLimit: 2
      activeDeadlineSeconds: 1200  # 单次备份最多 20 分钟
      ttlSecondsAfterFinished: 86400  # 完成后 1 天自动清理

      # 完成条件
      completions: 1
      parallelism: 1

      # Pod 模板
      template:
        metadata:
          labels:
            app: mysql-backup
        spec:
          restartPolicy: OnFailure

          containers:
            - name: backup
              image: mysql:8.0
              command:
                - sh
                - -c
                - |
                  set -e
                  echo "开始 MySQL 备份: $(date)"
                  
                  BACKUP_FILE="/backup/mysql-full-backup-$(date +%Y%m%d-%H%M%S).sql.gz"
                  
                  # 执行全量备份
                  mysqldump \
                    -h ${MYSQL_HOST} \
                    -u ${MYSQL_USER} \
                    -p${MYSQL_PASSWORD} \
                    --all-databases \
                    --single-transaction \
                    --routines \
                    --triggers \
                    --events \
                    | gzip > ${BACKUP_FILE}
                  
                  echo "备份完成: ${BACKUP_FILE} ($(du -h ${BACKUP_FILE} | cut -f1))"
                  
                  # 上传到对象存储（可选）
                  if [ -n "${S3_BUCKET}" ]; then
                    echo "上传备份到 S3..."
                    aws s3 cp ${BACKUP_FILE} s3://${S3_BUCKET}/mysql-backups/
                  fi
                  
                  echo "备份任务成功完成"

              env:
                - name: MYSQL_HOST
                  value: "mysql-primary.default.svc.cluster.local"
                - name: MYSQL_USER
                  valueFrom:
                    secretKeyRef:
                      name: mysql-credentials
                      key: username
                - name: MYSQL_PASSWORD
                  valueFrom:
                    secretKeyRef:
                      name: mysql-credentials
                      key: password
                - name: S3_BUCKET
                  value: "my-backup-bucket"

              resources:
                requests:
                  cpu: "200m"
                  memory: "256Mi"
                limits:
                  cpu: "1000m"
                  memory: "1Gi"

              volumeMounts:
                - name: backup-storage
                  mountPath: /backup

          volumes:
            - name: backup-storage
              persistentVolumeClaim:
                claimName: backup-pvc
```

## 11.5 控制器选择指南

### 11.5.1 控制器选择决策树

```
你的应用是什么类型？
│
├── 需要在每个节点上运行？
│   └── 是 → DaemonSet
│
├── 有状态应用（需要稳定标识/存储）？
│   └── 是 → StatefulSet
│
├── 一次性任务（执行完即结束）？
│   ├── 需要定时执行？
│   │   └── 是 → CronJob
│   └── 否 → Job
│
└── 无状态应用（常规 Web/API 服务）？
    └── Deployment
```

### 11.5.2 控制器对比表

| 维度 | Deployment | StatefulSet | DaemonSet | Job | CronJob |
|------|-----------|-------------|-----------|-----|---------|
| **核心用途** | 无状态应用 | 有状态应用 | 节点级代理 | 一次性任务 | 定时任务 |
| **Pod 数量** | 固定副本数 | 固定副本数 | 每节点 1 个 | 完成数 | 定时触发 |
| **Pod 名称** | 随机后缀 | 有序序号 | 随机后缀 | 随机后缀 | 随机后缀 |
| **存储** | 可选 | 稳定绑定 | 可选 | 可选 | 可选 |
| **网络** | 不稳定 | 稳定 DNS | 不稳定 | 不稳定 | 不稳定 |
| **生命周期** | 持续运行 | 持续运行 | 持续运行 | 完成即终止 | 定时执行 |
| **典型应用** | Web/API | 数据库/集群 | 日志/监控 | 数据迁移 | 备份/清理 |
| **重启策略** | Always | Always | Always | OnFailure/Never | OnFailure/Never |

### 11.5.3 选择建议

| 场景 | 推荐控制器 | 原因 |
|------|-----------|------|
| Nginx Web 服务 | Deployment | 无状态，需要灵活扩缩容 |
| MySQL 主从 | StatefulSet | 需要稳定标识和持久化存储 |
| Fluentd 日志收集 | DaemonSet | 每个节点都需要运行 |
| 数据迁移脚本 | Job | 一次性执行，不需要持续运行 |
| 日志清理 | CronJob | 周期性执行维护任务 |
| Redis Cluster | StatefulSet | 需要稳定节点名和有序初始化 |
| Node Exporter | DaemonSet | 每节点监控 |
| 批处理任务 | Job | 并行执行一次性任务 |
| 数据库备份 | CronJob | 定时执行备份脚本 |

### 实战 3：创建 Job 执行一次性数据迁移

**目标：** 创建一个 Job 执行数据库表结构迁移和数据导入。

```bash
# 第 1 步：创建迁移脚本 ConfigMap
cat > /tmp/migration-scripts.yaml << 'EOF'

  name: migration-scripts
data:
  migrate.sh: |
    #!/bin/bash
    set -e
    
    echo "========================================"
    echo " 数据迁移脚本"
    echo " 时间: $(date)"
    echo " Pod: ${POD_NAME}"
    echo " 分片: ${JOB_COMPLETION_INDEX}"
    echo "========================================"
    
    PGPASSWORD="${DB_PASSWORD}"
    
    # 建表
    echo "创建表结构..."
    psql -h ${DB_HOST} -U ${DB_USER} ${DB_NAME} << SQL
    CREATE TABLE IF NOT EXISTS users (
      id SERIAL PRIMARY KEY,
      username VARCHAR(50) NOT NULL,
      email VARCHAR(100) NOT NULL,
      created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
    );
    
    CREATE TABLE IF NOT EXISTS orders (
      id SERIAL PRIMARY KEY,
      user_id INTEGER REFERENCES users(id),
      amount DECIMAL(10,2) NOT NULL,
      status VARCHAR(20) DEFAULT 'pending',
      created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
    );
    SQL
    
    # 导入数据（每个分片处理不同范围）
    echo "导入分片 ${JOB_COMPLETION_INDEX} 的数据..."
    OFFSET=$((JOB_COMPLETION_INDEX * 2500))
    
    psql -h ${DB_HOST} -U ${DB_USER} ${DB_NAME} << SQL
    INSERT INTO users (username, email)
    SELECT 
      'user_' || i,
      'user_' || i || '@example.com'
    FROM generate_series(${OFFSET}, ${OFFSET} + 2499) AS i;
    
    INSERT INTO orders (user_id, amount, status)
    SELECT 
      (SELECT id FROM users ORDER BY random() LIMIT 1),
      (random() * 1000)::decimal(10,2),
      (ARRAY['pending', 'completed', 'cancelled'])[1 + floor(random() * 3)]
    FROM generate_series(1, 1000) AS i;
    SQL
    
    echo "分片 ${JOB_COMPLETION_INDEX} 迁移完成"
    echo "完成时间: $(date)"
EOF
```

**目标：** 创建一个 CronJob 每天凌晨 2:30 自动备份 MySQL 数据库。

```bash
# 第 1 步：创建备份存储 PVC

# 第 3 步：创建 CronJob
cat > /tmp/mysql-backup-cronjob.yaml << 'EOF'
apiVersion: batch/v1
kind: CronJob
metadata:
  name: mysql-backup
  labels:
    app: mysql-backup
    tier: maintenance
  annotations:
    description: "每天凌晨 2:30 备份 MySQL 数据库"
spec:
  schedule: "30 2 * * *"
  concurrencyPolicy: Forbid
  startingDeadlineSeconds: 300
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  suspend: false
  jobTemplate:
    spec:
      backoffLimit: 2
      activeDeadlineSeconds: 1200
      ttlSecondsAfterFinished: 86400
      template:
        metadata:
          labels:
            app: mysql-backup
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: mysql:8.0
              command:
                - sh
                - -c
                - |
                  set -e
                  BACKUP_DIR="/backup"
                  TIMESTAMP=$(date +%Y%m%d-%H%M%S)
                  BACKUP_FILE="${BACKUP_DIR}/mysql-backup-${TIMESTAMP}.sql.gz"
                  
                  echo "[$(date)] 开始 MySQL 全量备份"
                  
                  PGPASSWORD="${MYSQL_PASSWORD}"
                  mysqldump \
                    -h ${MYSQL_HOST} \
                    -u ${MYSQL_USER} \
                    --all-databases \
                    --single-transaction \
                    --routines \
                    --triggers \
                    --events \
                    --set-gtid-purged=OFF \
                    2>/dev/null | gzip > ${BACKUP_FILE}
                  
                  BACKUP_SIZE=$(du -h ${BACKUP_FILE} | cut -f1)
                  echo "[$(date)] 备份完成: ${BACKUP_FILE} (${BACKUP_SIZE})"
                  
                  # 清理 3 天前的备份
                  find ${BACKUP_DIR} -name "*.sql.gz" -mtime +3 -delete 2>/dev/null
                  echo "[$(date)] 旧备份清理完成"
                  echo "[$(date)] 备份任务成功"
              
              env:
                - name: MYSQL_HOST
                  value: "mysql-primary.default.svc.cluster.local"
                - name: MYSQL_USER
                  valueFrom:
                    secretKeyRef:
                      name: mysql-credentials
                      key: username
                - name: MYSQL_PASSWORD
                  valueFrom:
                    secretKeyRef:
                      name: mysql-credentials
                      key: password
              resources:
                requests:
                  cpu: "200m"
                  memory: "256Mi"
                limits:
                  cpu: "1000m"
                  memory: "1Gi"
              volumeMounts:
                - name: backup-storage
                  mountPath: /backup
          volumes:
            - name: backup-storage
              persistentVolumeClaim:
                claimName: backup-pvc
          affinity:
            nodeAffinity:
              preferredDuringSchedulingIgnoredDuringExecution:
                - weight: 100
                  preference:
                    matchExpressions:
                      - key: workload
                        operator: In
                        values:
                          - maintenance
EOF
```

## 11.7 常见问题排查

### Q1：DaemonSet 在某些节点上没有 Pod

```bash
# 检查节点状态
kubectl get nodes
# 确认节点是否 Ready

# 检查 nodeSelector 或 nodeAffinity 是否限制了节点
kubectl get daemonset <name> -o yaml | grep -A 10 nodeSelector
kubectl get daemonset <name> -o yaml | grep -A 10 nodeAffinity

# 检查节点标签
kubectl get nodes --show-labels

# 检查节点污点
kubectl describe node <node-name> | grep Taints

# 如果节点有污点，需要添加 tolerations
# 或移除污点：kubectl taint nodes <node-name> <key>-
```

### Q2：StatefulSet Pod 一直处于 Pending 状态

```bash
# 查看 Pod 事件
kubectl describe pod <statefulset-pod> | grep Events -A 20

# 常见原因：
# 1. PVC 绑定失败（存储类不存在或容量不足）
kubectl get pvc -l app=<label>
kubectl describe pvc <pvc-name>

# 2. 资源不足
kubectl describe pod <pod> | grep -A 5 "FailedScheduling"

# 3. PVC 未绑定
kubectl get storageclass
kubectl patch storageclass <name> -p '{"allowVolumeExpansion":true}'

# 4. 检查 volumeClaimTemplates 配置
kubectl get statefulset <name> -o yaml | grep -A 20 volumeClaimTemplates
```

### Q3：StatefulSet Pod 卡在创建中

```bash
# StatefulSet 按序创建，如果前一个 Pod 未就绪，后续 Pod 不会创建
# 检查前一个 Pod 状态
kubectl get pods -l app=<label>
kubectl describe pod <previous-pod>

# 常见原因：
# 1. 初始化脚本失败
# 2. 健康检查失败
# 3. 依赖服务未就绪

# 跳过当前 Pod（使用 OnDelete 策略手动删除）
kubectl delete pod <stuck-pod>
# StatefulSet 会重新创建该 Pod
```

### Q4：Job 一直处于 Running 状态

```bash
# 查看 Job 状态
kubectl get job <name>
kubectl describe job <name>

# 常见原因：
# 1. backoffLimit 未达到（重试次数过多）
# 2. Pod 持续失败但未达到 backoffLimit
kubectl get pods -l app=<label>
kubectl logs <failed-pod>

# 3. activeDeadlineSeconds 未设置
# 4. completions 未达到

# 查看失败的 Pod
kubectl get pods -l app=<label> --field-selector=status.phase=Failed

# 强制终止 Job
kubectl delete job <name>
# 关联的 Pod 也会被终止
```

### Q5：CronJob 没有按时执行

```bash
# 检查 CronJob 状态
kubectl get cronjob <name>
kubectl describe cronjob <name>

# 常见原因：
# 1. schedule 语法错误
# 使用 https://crontab.guru 验证 cron 表达式

# 2. suspend 设置为 true
kubectl patch cronjob <name> -p '{"spec":{"suspend":false}}'

# 3. 错过了起始截止时间
# 检查 startingDeadlineSeconds 设置

# 4. CronJob 控制器未运行
kubectl get pods -n kube-system -l k8s-app=kube-controller-manager

# 5. 历史 Job 记录已满
kubectl get job -l app=<label>

# 手动触发测试
kubectl create job --from=cronjob/<name> <name>-debug
```

### Q6：CronJob 并发执行导致冲突

```bash
# 使用 concurrencyPolicy 控制并发
# Forbid：跳过本次调度
kubectl patch cronjob <name> -p '{"spec":{"concurrencyPolicy":"Forbid"}}'

# Replace：用新 Job 替换运行中的
kubectl patch cronjob <name> -p '{"spec":{"concurrencyPolicy":"Replace"}}'

# Allow：允许多个并发（默认）
kubectl patch cronjob <name> -p '{"spec":{"concurrencyPolicy":"Allow"}}'

# 建议：备份/维护任务使用 Forbid，避免资源竞争
```

### Q7：StatefulSet 扩缩容失败

```bash
# StatefulSet 扩缩容是按序进行的
# 扩容：从 N-1 到 0 顺序创建
# 缩容：从 N-1 到 0 顺序删除

# 查看扩缩容状态
kubectl get statefulset <name>
# 观察 READY 列的变化

# 常见问题：
# 1. 缩容时 PVC 不会被删除（数据保留）
#    手动删除 PVC：kubectl delete pvc -l app=<label>
# 2. 缩容后重新扩容会使用之前的 PVC
#    如果需要全新数据，需要先删除 PVC
```

## 11.8 章节小结

### 核心概念总结

1. **DaemonSet**：每个 Node 运行一个 Pod，适用于节点级代理（日志、监控、网络）
2. **StatefulSet**：有状态应用控制器，提供稳定标识、有序部署、稳定存储
3. **Job**：一次性任务控制器，支持并行执行（parallelism / completions）
4. **CronJob**：定时任务控制器，基于 cron 表达式调度 Job

### 控制器选择速查表

| 需求 | 控制器 | 关键特性 |
|------|--------|----------|
| 每个节点运行一个 Pod | DaemonSet | nodeSelector / nodeAffinity |
| 有状态应用集群 | StatefulSet | 稳定标识 / PVC 模板 |
| 一次性批处理 | Job | parallelism / completions |
| 定时周期任务 | CronJob | schedule / concurrencyPolicy |
| 常规 Web/API | Deployment | 滚动更新 / 版本回滚 |

### 实战命令速查

```bash
# DaemonSet
kubectl apply -f daemonset.yaml
kubectl get daemonset -A
kubectl set image daemonset <name> <container>=<image>
kubectl rollout status daemonset/<name>

# StatefulSet
kubectl apply -f statefulset.yaml
kubectl get statefulset
kubectl scale statefulset <name> --replicas=N
kubectl get pvc -l app=<label>

# Job
kubectl apply -f job.yaml
kubectl get job
kubectl logs -l app=<label>
kubectl delete job <name>

# CronJob
kubectl apply -f cronjob.yaml
kubectl get cronjob
kubectl create job --from=cronjob/<name> <manual-name>
kubectl patch cronjob <name> -p '{"spec":{"suspend":true}}'
kubectl patch cronjob <name> -p '{"spec":{"schedule":"0 */4 * * *"}}'
```

### 最佳实践

- **DaemonSet**：使用 `nodeSelector` / `nodeAffinity` 精确控制节点范围，配合 `tolerations` 处理污点节点
- **StatefulSet**：务必配置 `volumeClaimTemplates` 实现数据持久化，使用 Headless Service 提供稳定 DNS
- **Job**：合理设置 `backoffLimit` 和 `activeDeadlineSeconds`，使用 `ttlSecondsAfterFinished` 自动清理
- **CronJob**：使用 `concurrencyPolicy: Forbid` 避免并发冲突，保留足够的历史记录用于排查
- **通用**：所有控制器配置合理的资源限制、健康检查和 Pod 标签，便于监控和管理
