### 1.1.3 K8s 诞生背景

2014 年 Google 开源 K8s 时，其内部 Borg 系统已运行了十多年，管理着数千节点、百万级容器。K8s 将 Borg 的核心设计理念（声明式 API、控制器模式、自愈能力）开源化，迅速成为容器编排的事实标准。

## 1.2 K8s 核心概念

### 1.2.1 Cluster（集群）

Cluster 是 K8s 的最大管理单元，由一组 Node 组成，对外提供统一的 API 入口。

```
                    ┌──────────────┐
                    │  K8s Cluster │
                    │              │
                    │  ┌────────┐  │
                    │  │ Node 1 │  │
                    │  │(Worker)│  │
                    │  └────────┘  │
                    │  ┌────────┐  │
                    │  │ Node 2 │  │
                    │  │(Worker)│  │
                    │  └────────┘  │
                    │  ┌────────┐  │
                    │  │ Node N │  │
                    │  │(Worker)│  │
                    │  └────────┘  │
                    └──────────────┘
```

### 1.2.2 Node（节点）

Node 是集群中的一台物理机或虚拟机，是 Pod 实际运行的载体。

- **Master Node（已废弃概念）**：早期 K8s 中运行 Control Plane 组件的节点，现称 Control Plane Node
- **Worker Node**：运行业务 Pod 的节点

### 1.2.3 Pod

Pod 是 K8s 中最小的可部署计算单元，一个 Pod 可以包含一个或多个紧密协作的容器。

**Pod 的关键特性：**

- 同一 Pod 内的容器**共享网络命名空间**（IP 地址、端口）
- 同一 Pod 内的容器**共享存储卷**（Volume）
- Pod 有独立的生命周期状态：Pending → Running → Succeeded/Failed

```yaml
# 典型的单容器 Pod 定义
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    app: nginx
spec:
  containers:
    - name: nginx
      image: nginx:1.25
      ports:
        - containerPort: 80
      resources:
        requests:
          memory: "64Mi"
          cpu: "250m"
        limits:
          memory: "128Mi"
          cpu: "500m"
```

### 1.2.4 Container（容器）

Container 是 Pod 内的实际运行单元，基于容器运行时（containerd、CRI-O、Docker）隔离。

> **Pod vs Container 设计哲学**：K8s 选择 Pod 作为最小单元而非直接管理 Container，是因为某些场景需要多个容器紧密协作（如主容器 + 日志 sidecar 容器），共享网络和存储比通过 Service 通信更高效。

### 1.3.2 Control Plane 组件详解

#### API Server

API Server 是整个集群的**唯一入口点**，所有组件间的通信都经过它。

**核心职责：**
- 提供 RESTful API，支持 Kubernetes 资源的 CRUD 操作
- 承担认证（Authentication）、授权（Authorization）、准入控制（Admission Control）
- 所有其他组件（Scheduler、Controller Manager、Kubelet）通过 API Server 与 etcd 交互

```bash
# 查看 API Server 支持的 API 版本
kubectl api-versions

# 查看 API Server 支持的资源类型
kubectl api-resources

# 直接与 API Server 交互
kubectl get --raw="/api/v1/namespaces" | jq
```

#### etcd

etcd 是 K8s 的**分布式键值存储**，保存集群的所有状态数据。

**核心职责：**
- 存储所有集群状态（Pod 定义、Service 配置、Secret 等）
- 基于 Raft 协议实现强一致性
- 仅 API Server 可直接读写 etcd

**etcd 数据结构示例：**
```
/registry/pods/default/nginx-pod → {metadata, spec, status}
/registry/services/default/nginx-svc → {metadata, spec, status}
/registry/secrets/default/db-password → {data}
```

> **生产建议**：etcd 必须部署奇数节点（3 或 5 节点）以保证 Raft 仲裁，且需要使用高速 SSD 存储。

#### Scheduler（调度器）

Scheduler 负责将**未调度的 Pod 分配到合适的 Worker Node**。

**调度流程：**
1. 监听 API Server，发现待调度的 Pod（`spec.nodeName` 为空）
2. 执行过滤（Predicate）：排除资源不足、标签不匹配的节点
3. 执行打分（Priority）：根据资源利用率、亲和性等对候选节点打分
4. 选择得分最高的节点，将结果写入 API Server

```
  待调度 Pod        Scheduler              Worker Node
  ┌─────────┐     ┌──────────┐            ┌──────────┐
  │ Pod A   │────▶│ 过滤筛选 │──选择──▶   │  Node 2  │
  └─────────┘     │ 打分排序 │            └──────────┘
                  └──────────┘                 │
                                               │ 绑定
                                               ▼
                                          API Server
                                               │
                                               ▼
                                           etcd
```

#### Controller Manager

Controller Manager 运行一组控制器，每个控制器负责维护特定资源的**期望状态**。

**核心内置控制器：**

| 控制器 | 职责 |
|--------|------|
| Node Controller | 监控节点状态，节点不可达时驱逐 Pod |
| Replication Controller | 维护指定数量的 Pod 副本 |
| Endpoint Controller | 根据 Service/Pod 的关系维护 Endpoints |
| ServiceAccount Controller | 管理 namespace 中的 ServiceAccount |
| Deployment Controller | 管理 Deployment 的副本和滚动升级 |

**控制器工作循环：**
```
  期望状态            控制器            实际状态
  ┌─────────┐       ┌──────────┐      ┌──────────┐
  │ replicas│──────▶│ 对比差异 │─────▶│ replicas │
  │    3    │       │ 创建/删除│      │    2     │
  └─────────┘       └──────────┘      └──────────┘
                            │
                            ▼
                       API Server
```

### 1.3.3 Worker Node 组件详解

#### Kubelet

Kubelet 是 Worker Node 上的**主要代理**，负责管理节点上 Pod 的生命周期。

**核心职责：**
- 通过 API Server 获取分配给本节点的 Pod 定义
- 调用 Container Runtime 创建和管理容器
- 定期向 Control Plane 汇报节点和 Pod 状态（心跳）
- 执行 Liveness、Readiness、Startup 探针

```bash
# 查看节点状态详情
kubectl describe node <node-name>

# 通过 kubelet API 直接查看节点信息
curl -k https://<node-ip>:10250/pods
curl -k https://<node-ip>:10250/node
```

#### Kube-Proxy

Kube-Proxy 负责在每个节点上维护**网络规则**，实现 Service 的访问路由。

**三种模式对比：**

| 模式 | 实现方式 | 性能 | 适用场景 |
|------|---------|------|---------|
| iptables | 修改 iptables 规则 | 中 | 默认模式，小规模集群 |
| IPVS | IP Virtual Server | 高 | 大规模集群（>1000 服务） |
| userspace | 应用层代理 | 低 | 调试/兼容场景 |

```
                  Client Request
                        │
                        ▼
               Kube-Proxy (Node)
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
      Pod A (Node1)  Pod B (Node2)  Pod C (Node3)
      10.244.1.5    10.244.2.3    10.244.3.7
```

#### Container Runtime

Container Runtime 是容器的**实际运行引擎**。

**CRI（Container Runtime Interface）：**
K8s 通过 CRI 接口抽象容器运行时，支持多种实现：

```
  Kubelet
    │
    ▼
  CRI Interface ──────── containerd (推荐)
    │                 ├── CRI-O
    │                 ├── Docker (已废弃)
    │                 └── Mirantis cri-dockerd
    │
    ▼
  OCI Interface ───────── runc
                      ├── Kata Containers
                      └── gVisor
```

## 1.4 Pod 创建全流程

### 1.4.1 完整链路图

```
Step 1: kubectl apply -f nginx-pod.yaml
    │
    ▼
Step 2: kubectl → API Server
        · 发送 Pod 创建请求
        · API Server 进行认证/授权/准入控制
    │
    ▼
Step 3: API Server → etcd
        · 将 Pod 定义持久化存储
        · 返回 201 Created
    │
    ▼
Step 4: Scheduler 监听未调度 Pod
        · 发现 Pod 的 spec.nodeName 为空
        · 执行调度算法，选择目标节点
        · 将 nodeName 写入 Pod 定义
    │
    ▼
Step 5: API Server 更新 etcd 中的 Pod（绑定节点）
    │
    ▼
Step 6: Kubelet 监听本节点的 Pod
        · 发现新分配的 Pod
        · 拉取镜像 → 创建容器
        · 执行探针检查
    │
    ▼
Step 7: Kubelet → API Server
        · 更新 Pod 状态（Pending → ContainerCreating → Running）
    │
    ▼
Step 8: Pod Running，服务可用 ✅
```

### 1.4.2 各阶段详解

**Phase 1: 用户提交请求**
```bash
kubectl apply -f nginx-pod.yaml
```

**Phase 2: API Server 处理**
```bash
# API Server 处理流程
# 1. 认证（Authentication）：验证调用方身份
# 2. 授权（Authorization）：检查调用方权限
# 3. 准入控制（Admission Control）：执行 Mutating/Validating Webhook
# 4. 持久化：写入 etcd
# 5. 通知：返回成功响应
```

**Phase 3: Scheduler 调度**
```bash
# Scheduler 调度决策日志
I0728 10:00:00.000] scheduler.go:301 "Attempting to schedule pod" pod="default/nginx-pod"
I0728 10:00:00.001] scheduler.go:155 "Filtering" pod="default/nginx-pod" nodes=3
I0728 10:00:00.002] scheduler.go:155 "Scoring" pod="default/nginx-pod" nodes=2
I0728 10:00:00.003] scheduler.go:155 "Selected node" pod="default/nginx-pod" node="worker-node-2"
```

**Phase 4: Kubelet 创建容器**
```bash
# Kubelet 操作流程
# 1. 创建 Pod 目录结构
# 2. 拉取镜像（如本地不存在）
# 3. 创建容器（Pause 容器 + Nginx 容器）
# 4. 启动容器
# 5. 执行探针检查
```

**Phase 5: 状态汇报**
```bash
# 查看 Pod 状态变化
kubectl get pods -w
# NAME        READY   STATUS              RESTARTS   AGE
# nginx-pod   0/1     ContainerCreating   0          1s
# nginx-pod   1/1     Running             0          3s
```

## 1.5 kubectl 基础使用

### 1.5.1 资源操作模式

kubectl 遵循 **`动词 + 资源`** 的操作模式：

```
kubectl <verb> <resource> <name> [flags]
```

**常用动词：**

| 动词 | 说明 | 示例 |
|------|------|------|
| get | 查询资源 | `kubectl get pods` |
| create | 创建资源 | `kubectl create -f file.yaml` |
| apply | 创建或更新资源（声明式） | `kubectl apply -f file.yaml` |
| delete | 删除资源 | `kubectl delete pod nginx-pod` |
| describe | 查看资源详情 | `kubectl describe pod nginx-pod` |
| logs | 查看容器日志 | `kubectl logs nginx-pod` |
| exec | 在容器中执行命令 | `kubectl exec nginx-pod -- bash` |
| expose | 创建 Service | `kubectl expose pod nginx-pod --port=80` |
| scale | 扩缩容 | `kubectl scale deployment nginx --replicas=5` |
| edit | 在线编辑资源 | `kubectl edit pod nginx-pod` |
| patch | 部分更新资源 | `kubectl patch pod nginx-pod -p '{"spec":{"..."}}'` |
| rollout | 管理部署滚动 | `kubectl rollout status deployment nginx` |
| port-forward | 端口转发 | `kubectl port-forward pod/nginx-pod 8080:80` |
| top | 查看资源使用 | `kubectl top pods` |

**常用资源类型：**

| 资源 | 缩写 | 说明 |
|------|------|------|
| Pods | po | Pod 资源 |
| Services | svc | 服务发现和负载均衡 |
| Deployments | deploy | 管理无状态应用 |
| StatefulSets | sts | 管理有状态应用 |
| DaemonSets | ds | 每个节点运行一个 Pod |
| ConfigMaps | cm | 非敏感配置 |
| Secrets | sec | 敏感信息 |
| Namespaces | ns | 资源隔离 |
| Nodes | no | 集群节点 |
| ReplicaSets | rs | 副本控制器 |
| Ingresses | ing | HTTP/HTTPS 路由 |
| PersistentVolumes | pv | 持久存储 |

### 1.5.2 kubectl 核心子命令速查

```bash
# 集群信息
kubectl cluster-info                    # 查看集群信息
kubectl version --client                # 查看客户端版本
kubectl config get-contexts             # 查看所有上下文

# 命名空间操作
kubectl get namespaces

kubectl get pods -o wide                # 输出更多信息
kubectl get pods -o yaml                # 输出 YAML 格式
kubectl get pods -l app=nginx           # 按标签过滤
kubectl describe pod <name>             # 查看 Pod 详情
kubectl logs <pod-name>                 # 查看日志
kubectl logs <pod-name> -c <container>  # 指定容器日志
kubectl logs -f <pod-name>              # 实时跟踪日志

# Service 操作
kubectl get services

# 节点操作

kubectl drain <node> --delete-emptydir-data --ignore-daemonsets  # 驱逐 Pod

# 标签与注解
kubectl label pod <name> env=prod
kubectl annotate pod <name> owner=team-a

# 资源使用
kubectl top pods
kubectl top nodes
```

### 1.6.3 理解动词 + 资源操作模式

```bash
# === GET ===
kubectl get pods                              # 获取所有 Pod
kubectl get pod nginx-pod                     # 获取指定 Pod
kubectl get pods -o json                      # JSON 格式输出
kubectl get pods --no-headers                 # 无表头输出
kubectl get pods | grep nginx                 # 管道过滤
kubectl get pods -o name                      # 仅输出资源名

# === CREATE ===
kubectl create -f pod.yaml                    # 从文件创建
kubectl create -f https://example.com/pod.yaml  # 从 URL 创建
echo 'apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  containers:
  - name: nginx
    image: nginx' | kubectl create -f -        # 从 stdin 创建

# === APPLY ===
kubectl apply -f deployment.yaml              # 声明式创建/更新
kubectl apply -f ./k8s/                       # 应用目录下所有 YAML
kubectl apply -f deployment.yaml --dry-run=client  # 试运行

# === DELETE ===
kubectl delete pod nginx-pod                  # 删除指定 Pod
kubectl delete pods -l app=nginx              # 按标签删除
kubectl delete pod --all                      # 删除所有 Pod
kubectl delete -f pod.yaml                    # 根据文件删除
kubectl delete deployment nginx --cascade=orphan  # 级联删除控制

# === 批量操作 ===
kubectl get pods -l app=nginx -o name | xargs kubectl delete  # 批量删除
kubectl get pods -l app=nginx -o name | xargs -I {} kubectl exec {} -- date  # 批量执行命令
```

### 1.6.4 kubectl 输出格式化

```bash
# 自定义列输出
kubectl get pods -o custom-columns='NAME:.metadata.name,STATUS:.status.phase,IP:.status.podIP'

# 排序输出
kubectl get pods --sort-by='.metadata.name'
kubectl get pods --sort-by='.status.startTime'

# 字段过滤
kubectl get pods --field-selector=status.phase=Running
kubectl get pods --field-selector=spec.nodeName=worker-1

# 结合 jsonpath 提取特定字段
kubectl get pods -o jsonpath='{.items[*].metadata.name}'
kubectl get pods -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.phase}{"\n"}{end}'
```

### Q1: kubectl 无法连接集群

```bash
# 检查 kubeconfig
kubectl config view

# 检查上下文
kubectl config current-context

# 测试连接
kubectl cluster-info
```

## 1.8 章节小结

### 核心要点回顾

1. **演进脉络**：手工管理 → Docker（容器化）→ Compose/Swarm（单机/简单编排）→ Kubernetes（生产级容器编排）
2. **核心概念**：Cluster（集群）> Node（节点）> Pod（最小部署单元）> Container（容器）
3. **架构分层**：
   - Control Plane：API Server（入口）+ etcd（存储）+ Scheduler（调度）+ Controller Manager（控制循环）
   - Worker Node：Kubelet（代理）+ Kube-Proxy（网络）+ Container Runtime（运行时）
4. **Pod 创建流程**：`kubectl apply` → API Server → etcd → Scheduler → Kubelet → Container Runtime → Pod Running
5. **kubectl 操作模式**：`动词 + 资源`，常用动词包括 get/create/apply/delete/describe/logs/exec
