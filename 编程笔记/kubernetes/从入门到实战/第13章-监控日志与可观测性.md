## 13.1 可观测性三大支柱

### 13.1.1 什么是可观测性

可观测性（Observability）是指通过系统外部的信号推断系统内部状态的能力。在 Kubernetes 中，可观测性主要围绕三大支柱构建：

```
┌─────────────────────────────────────────────────────────────┐
│                    可观测性三大支柱                           │
│                                                             │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐      │
│  │   Metrics    │  │    Logs      │  │   Traces     │      │
│  │   指标       │  │    日志      │  │   追踪       │      │
│  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘      │
│         │                 │                 │              │
│         ▼                 ▼                 ▼              │
│  · 数值型数据         · 事件记录          · 请求链路        │
│  · 聚合趋势分析       · 详细上下文        · 服务依赖        │
│  · 实时告警           · 问题定位          · 性能瓶颈        │
│  · 资源监控           · 审计追踪          · 故障诊断        │
│                                                             │
│  典型工具:                                                │
│  Prometheus / Grafana  ELK / Loki / Fluentd  Jaeger / Zipkin │
└─────────────────────────────────────────────────────────────┘
```

### 13.1.2 三大支柱对比

| 维度 | Metrics（指标） | Logs（日志） | Traces（追踪） |
|------|----------------|-------------|---------------|
| **数据类型** | 数值型、可聚合 | 文本型、不可变 | 请求链路、可关联 |
| **查询方式** | PromQL / 数学运算 | 全文检索 / 结构化查询 | 链路查询 / 拓扑分析 |
| **存储成本** | 低（聚合后） | 高（全量存储） | 中（采样存储） |
| **适用场景** | 实时监控、告警 | 问题排查、审计 | 性能诊断、依赖分析 |
| **典型工具** | Prometheus、Grafana | ELK、Loki、Fluentd | Jaeger、Zipkin、Tempo |

## 13.2 Metrics 监控体系

### 13.2.1 Prometheus 架构

Prometheus 是 CNCF 毕业项目，是 Kubernetes 生态中最主流的监控解决方案。

#### 核心组件说明

| 组件 | 功能 | 采集对象 |
|------|------|---------|
| **Prometheus Server** | 数据采集、存储、查询 | 通过 Scrape 机制拉取指标 |
| **Node Exporter** | 主机级指标采集 | CPU、内存、磁盘、网络 |
| **cAdvisor** | 容器级指标采集 | 容器 CPU、内存、文件系统、网络 |
| **kube-state-metrics** | Kubernetes 对象状态指标 | Pod、Deployment、Node 等状态 |
| **Grafana** | 可视化与告警 | 对接 Prometheus 数据源，展示仪表盘 |

### 13.2.2 PromQL 基础查询语言

PromQL（Prometheus Query Language）是 Prometheus 的查询语言，用于选择、过滤和聚合时序数据。

#### 基础查询示例

```promql
# 1. 查询 CPU 使用率（按节点）
100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)

# 2. 查询内存使用率
(node_memory_MemTotal_bytes - node_memory_MemAvailable_bytes) / node_memory_MemTotal_bytes * 100

# 3. 查询 Pod 状态
kube_pod_status_phase{phase="Running"} == 1

# 4. 查询 Pod 重启次数
increase(kube_pod_container_status_restarts_total[15m]) > 0

# 5. 查询容器 CPU 使用率
rate(container_cpu_usage_seconds_total[5m]) * 100

# 6. 查询网络流量
rate(node_network_receive_bytes_total{device!="lo"}[5m])

# 7. 查询磁盘使用率
(node_filesystem_size_bytes - node_filesystem_avail_bytes) / node_filesystem_size_bytes * 100

# 8. 按命名空间聚合
sum by (namespace) (rate(container_cpu_usage_seconds_total[5m]))
```

#### 常用 PromQL 函数

| 函数 | 说明 | 示例 |
|------|------|------|
| `rate()` | 计算增长率 | `rate(metric[5m])` |
| `irate()` | 计算瞬时增长率 | `irate(metric[5m])` |
| `increase()` | 计算增量 | `increase(metric[15m])` |
| `sum()` | 求和聚合 | `sum(metric)` |
| `avg()` | 平均值聚合 | `avg(metric)` |
| `max()` | 最大值聚合 | `max(metric)` |
| `topk()` | 取前 K 个 | `topk(5, metric)` |
| `histogram_quantile()` | 分位数计算 | `histogram_quantile(0.99, rate(histogram))` |

## 13.3 日志收集体系

### 13.3.1 方案对比

#### ELK vs Loki vs Fluentd

| 维度 | ELK（Elasticsearch + Logstash + Kibana） | Loki + Promtail | Fluentd |
|------|----------------------------------------|-----------------|---------|
| **架构** | 中心化处理，Logstash 收集转发 | 轻量 Agent + 集中存储 | DaemonSet 模式 |
| **存储** | Elasticsearch（全文检索） | 对象存储（S3/GCS） | 可插拔存储 |
| **查询** | Kibana（Lucene 查询） | LogQL（类 Log 查询） | 插件查询 |
| **资源占用** | 高（需 Logstash 集群） | 低（Agent 轻量） | 中 |
| **部署复杂度** | 高 | 低 | 中 |
| **适用场景** | 复杂日志分析、全文检索 | 云原生、与 Grafana 集成 | 通用日志收集 |
| **K8s 集成** | 需要额外配置 | 原生支持 | 原生支持 |

#### 推荐方案

- **中小规模集群**：Loki + Promtail，轻量且与 Grafana 无缝集成
- **大规模集群**：ELK，功能强大但资源开销大
- **需要丰富过滤**：Fluentd，插件生态丰富

### 13.3.3 日志查询与分析

#### 使用 kubectl 查看 Pod 日志

```bash
# 查看 Pod 日志
kubectl logs <pod-name> -n <namespace>

# 查看最近 100 行日志
kubectl logs --tail=100 <pod-name> -n <namespace>

# 查看最近 10 分钟的日志
kubectl logs --since=10m <pod-name> -n <namespace>

# 查看上一个容器的日志（CrashLoopBackOff 场景）
kubectl logs <pod-name> -n <namespace> --previous

# 实时跟踪日志
kubectl logs -f <pod-name> -n <namespace>

# 多 Pod 日志（Label 选择器）
kubectl logs -l app=my-app -n <namespace> --prefix --timestamps
```

#### 使用 LogQL 查询 Loki

```logql
# 基础日志过滤
{job="kubernetes-pods", namespace="production"} |= "error"

# 正则匹配
{namespace="production", app="api-server"} |~ "ERROR|WARN"

# 排除特定日志
{namespace="production"} != "healthcheck" != "metrics"

# 标签过滤
{namespace="production", pod_name="api-server-*"} |= "timeout"

# 聚合统计
sum(count_over_time({namespace="production"} |= "error" [1m]))

# 按标签分组统计
sum by (app) (count_over_time({namespace="production"} |= "error" [5m]))
```

## 13.4 分布式追踪体系

### 13.4.1 分布式追踪架构

分布式追踪用于跟踪请求在微服务架构中的完整调用链路。

```
┌─────────────────────────────────────────────────────────────┐
│                    分布式追踪架构                             │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │                    应用层（Instrumented App）         │   │
│  │                                                     │   │
│  │  ┌──────────┐  ┌──────────┐  ┌──────────┐          │   │
│  │  │ Service A │  │ Service B │  │ Service C │          │   │
│  │  │ (API网关) │  │ (业务服务)│  │ (数据服务)│          │   │
│  │  └─────┬────┘  └─────┬────┘  └─────┬────┘          │   │
│  │        │  Span 传播   │  Span 传播   │               │   │
│  │        └─────────────┼─────────────┘               │   │
│  │                      │                               │   │
│  └──────────────────────┼───────────────────────────────┘   │
│                         │                                   │
│              Trace Context 传播（HTTP Header）                │
│                         │                                   │
│                         ▼                                   │
│  ┌─────────────────────────────────────────────────────┐   │
│  │              OpenTelemetry SDK（语言库）              │   │
│  │  · Go / Java / Python / Node.js 等                  │   │
│  │  · 自动插桩 / 手动埋点                               │   │
│  │  · Span 生成 / 上下文传播                            │   │
│  └─────────────────────────┬───────────────────────────┘   │
│                             │                               │
│                    OTLP/gRPC 上报                           │
│                             │                               │
│                             ▼                               │
│  ┌─────────────────────────────────────────────────────┐   │
│  │              Jaeger / Zipkin / Tempo（后端存储）       │   │
│  │                                                     │   │
│  │  ┌────────────┐  ┌────────────┐  ┌────────────┐   │   │
│  │  │ 接收服务   │  │ 存储（ES/  │  │ 查询/UI    │   │   │
│  │  │ Collector  │  │  Cassandra│  │            │   │   │
│  │  └────────────┘  └────────────┘  └────────────┘   │   │
│  └─────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

### 13.4.2 核心概念

| 概念 | 说明 |
|------|------|
| **Trace** | 一次完整请求的调用链路 |
| **Span** | 链路中的一个操作单元（如一次函数调用、一次 RPC） |
| **Trace Context** | 用于跨服务传播的上下文信息（TraceID + SpanID） |
| **Sampling** | 采样策略，决定哪些 Trace 被记录 |
| **Instrumentation** | 插桩，指在应用代码中添加追踪逻辑 |

#### OpenTelemetry 应用集成示例（Go）

```go
// otel-integration.go
package main

import (
    "context"
    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/exporters/otlp/otlptrace"
    "go.opentelemetry.io/otel/exporters/otlp/otlptrace/otlptracegrpc"
    "go.opentelemetry.io/otel/sdk/resource"
    sdktrace "go.opentelemetry.io/otel/sdk/trace"
    semconv "go.opentelemetry.io/otel/semconv/v1.21.0"
)

func initTracer() (*sdktrace.TracerProvider, error) {
    client := otlptracegrpc.NewClient(
        otlptracegrpc.WithEndpoint("jaeger-collector.tracing:4317"),
        otlptracegrpc.WithInsecure(),
    )
    
    exporter, err := otlptrace.New(context.Background(), client)
    if err != nil {
        return nil, err
    }
    
    resource, _ := resource.New(context.Background(),
        resource.WithAttributes(
            semconv.ServiceNameKey.String("my-service"),
            semconv.ServiceVersionKey.String("1.0.0"),
            semconv.DeploymentEnvironmentKey.String("production"),
        ),
    )
    
    tp := sdktrace.NewTracerProvider(
        sdktrace.WithBatcher(exporter),
        sdktrace.WithResource(resource),
        sdktrace.WithSampler(sdktrace.AlwaysSample()),
    )
    
    otel.SetTracerProvider(tp)
    otel.SetTextMapPropagator(propagation.NewCompositeTextMapPropagator(
        propagation.TraceContext{},
        propagation.Baggage{},
    ))
    
    return tp, nil
}

func main() {
    tp, err := initTracer()
    if err != nil {
        panic(err)
    }
    defer tp.Shutdown(context.Background())
    
    tracer := otel.Tracer("my-service")
    
    ctx, span := tracer.Start(context.Background(), "handle-request")
    defer span.End()
    
    // 业务逻辑
    doSomething(ctx)
}
```

## 13.5 常用监控指标

### 13.5.1 核心监控指标清单

| 类别 | 指标 | PromQL 表达式 | 告警阈值 |
|------|------|---------------|---------|
| **CPU** | 节点 CPU 使用率 | `100 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100` | > 85% |
| **CPU** | Pod CPU 使用率 | `sum by (pod) (rate(container_cpu_usage_seconds_total[5m])) * 100` | > 80% |
| **内存** | 节点内存使用率 | `(MemTotal - MemAvailable) / MemTotal * 100` | > 90% |
| **内存** | Pod 内存使用率 | `container_memory_working_set_bytes / container_spec_memory_limit_bytes * 100` | > 85% |
| **磁盘** | 磁盘使用率 | `(node_filesystem_size - node_filesystem_avail) / node_filesystem_size * 100` | > 85% |
| **网络** | 网络接收流量 | `rate(node_network_receive_bytes_total[5m])` | 按场景 |
| **网络** | 网络发送流量 | `rate(node_network_transmit_bytes_total[5m])` | 按场景 |
| **Pod** | Pod 重启次数 | `increase(kube_pod_container_status_restarts_total[15m])` | > 3 次 |
| **Pod** | Pod 状态异常 | `kube_pod_status_phase{phase="Failed"} == 1` | 任何 Failed |
| **节点** | 节点 NotReady | `kube_node_status_condition{condition="Ready", status="true"} == 0` | 任何 NotReady |

### 13.5.2 告警规则配置

```yaml
# prometheus-alert-rules.yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: kubernetes-alert-rules
  namespace: monitoring
spec:
  groups:
    - name: node-alerts
      rules:
        - alert: NodeHighCPUUsage
          expr: 100 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100 > 85
          for: 5m
          labels:
            severity: warning
          annotations:
            summary: "节点 {{ $labels.instance }} CPU 使用率过高"

      rules:
        - alert: PodRestartingFrequently
          expr: increase(kube_pod_container_status_restarts_total[15m]) > 3

            summary: "Pod {{ $labels.namespace }}/{{ $labels.pod }} 频繁重启"

          labels:
            severity: critical

            summary: "Pod {{ $labels.namespace }}/{{ $labels.pod }} OOMKilled"

        - alert: NodeNotReady
```

### 实战 6：实现简单的告警规则

```bash
# 1. 创建 PrometheusRule 资源
kubectl apply -f - << 'EOF'

kind: PrometheusRule
metadata:
  name: custom-alert-rules
  namespace: monitoring
spec:
  groups:
    - name: pod-health-alerts
      interval: 30s
      rules:
        - alert: PodRestartTooManyTimes
          expr: increase(kube_pod_container_status_restarts_total[10m]) > 5
          for: 5m
          labels:
            severity: warning
            team: platform
          annotations:
            summary: "Pod {{ $labels.namespace }}/{{ $labels.pod }} 频繁重启"
            description: "Pod {{ $labels.namespace }}/{{ $labels.pod }} 在过去 10 分钟内重启了 {{ $value }} 次，请检查容器日志。"
            runbook_url: "https://wiki.example.com/troubleshooting/pod-restart"
        
        - alert: PodOOMKilledCritical
          expr: kube_pod_container_status_last_terminated_reason{reason="OOMKilled"} == 1
          for: 1m
          labels:
            severity: critical
            team: platform
          annotations:
            summary: "Pod {{ $labels.namespace }}/{{ $labels.pod }} 因 OOMKilled 终止"
            description: "容器 {{ $labels.container }} 因内存不足被杀，请增加内存限制或排查内存泄漏。"
        
        - alert: HighCPUUsage
          expr: 100 - avg by (pod) (rate(container_cpu_usage_seconds_total{container!=""}[5m])) * 100 > 80
          for: 10m
          labels:
            severity: warning
          annotations:
            summary: "Pod {{ $labels.namespace }}/{{ $labels.pod }} CPU 使用率过高"
            description: "CPU 使用率达到 {{ $value }}%，持续 10 分钟"

    - name: node-resource-alerts
      interval: 30s
      rules:
        - alert: NodeCPUPressure

          for: 10m
          labels:
            severity: warning
```

## 13.7 常见问题排查

### 13.7.1 Prometheus 相关

| 问题 | 排查方法 |
|------|---------|
| Prometheus Targets Down | 1. 检查 Service/ServiceMonitor 是否正确配置<br>2. 检查网络连通性<br>3. 检查抓取端口是否暴露 |
| 内存不足 OOM | 1. 增加 `--storage.tsdb.retention.time` 减少数据保留时间<br>2. 增加 Prometheus 内存限制<br>3. 使用 `--web.enable-lifecycle` 开启删除 API |
| 数据延迟 | 1. 检查 `scrape_interval` 配置<br>2. 检查 Prometheus Server CPU/内存使用率 |
| TSDB 损坏 | 1. 使用 `tsdb_tool` 工具修复<br>2. 从备份恢复数据 |

### 13.7.2 Grafana 相关

| 问题 | 排查方法 |
|------|---------|
| 无法连接 Prometheus | 1. 检查数据源 URL 是否正确<br>2. 检查网络和 DNS 解析<br>3. 检查 Prometheus 是否允许远程访问 |
| 仪表盘无数据 | 1. 验证 PromQL 查询语句<br>2. 检查时间范围是否正确<br>3. 检查标签匹配 |
| 仪表盘权限问题 | 1. 检查 Grafana 用户角色<br>2. 检查数据源权限 |

### 13.7.3 日志相关

| 问题 | 排查方法 |
|------|---------|
| Promtail 不采集日志 | 1. 检查 DaemonSet 是否运行<br>2. 检查 `scrape_configs` 配置<br>3. 检查路径映射是否正确 |
| Loki 查询超时 | 1. 缩小查询时间范围<br>2. 使用 `query_range` 分块查询<br>3. 增加 Loki 资源 |
| 日志丢失 | 1. 检查 Promtail 缓冲区<br>2. 检查 Loki 写入速率限制<br>3. 检查磁盘空间 |

### 13.7.4 告警相关

| 问题 | 排查方法 |
|------|---------|
| 告警未触发 | 1. 检查 PrometheusRule 是否正确<br>2. 在 Prometheus UI 测试查询<br>3. 检查 `for` 持续时间 |
| 告警未发送 | 1. 检查 Alertmanager 配置<br>2. 检查通知渠道是否可用<br>3. 查看 Alertmanager 日志 |
| 告警风暴 | 1. 使用 `group_by` 聚合<br>2. 配置 `inhibit_rules` 抑制<br>3. 设置合理的 `repeat_interval` |

### 核心要点

1. **可观测性三大支柱**：Metrics（指标监控）、Logs（日志分析）、Traces（链路追踪）各有侧重，互为补充
2. **Prometheus 架构**：采用 Pull 模式采集指标，通过 Service Discovery 自动发现目标，TSDB 时序存储高效
3. **日志方案选型**：中小规模推荐 Loki + Promtail（轻量、与 Grafana 集成好），大规模推荐 ELK
4. **分布式追踪**：OpenTelemetry 是未来标准，Jaeger/Zipkin 是当前主流后端
5. **告警配置**：合理设置阈值和持续时间，避免告警风暴；配置抑制规则处理关联告警
6. **实战要点**：优先使用 Helm 部署，利用社区预置 Dashboard 快速搭建，逐步定制化
