# 第9章：调度机制与节点管理

完成本章学习后，你将能够：

1. 深入理解 K8s Scheduler 的调度流程：预选、优选、抢占

## 9.1 Scheduler 调度流程详解

### 9.1.1 调度器概述

K8s Scheduler 是一个默认运行在控制平面的组件，负责为尚未绑定节点的 Pod 选择合适的节点。调度过程分为三个核心阶段：

```
待调度 Pod
    │
    ▼
┌─────────────────────────────────┐
│  阶段一：预选（Predicates）      │
│  过滤掉不满足条件的节点          │
└─────────────┬───────────────────┘
              │
              ▼
┌─────────────────────────────────┐
│  阶段二：优选（Priorities）      │
│  对剩余节点打分排序             │
└─────────────┬───────────────────┘
              │
              ▼
┌─────────────────────────────────┐
│  阶段三：抢占（Preemption）      │
│  高优先级 Pod 抢占低优先级 Pod   │
└─────────────────────────────────┘
```

### 9.1.2 预选（Predicates）—— 节点过滤

预选阶段会检查每个节点是否满足 Pod 的运行条件，不满足的节点会被排除。

**常见的预选检查项**：

| 检查项 | 说明 |
|--------|------|
| **资源不足** | 节点的 CPU/内存剩余量是否满足 Pod 的 requests |
| **端口冲突** | Pod 请求的 hostPort 是否与节点上已有 Pod 冲突 |
| **Volume 限制** | Pod 引用的 Volume 是否能在节点挂载 |
| **NodeName** | Pod 是否指定了 nodeName，且与当前节点匹配 |
| **Node Affinity** | 节点是否满足 Pod 的 Node Affinity 要求 |
| **Taint/Toleration** | 节点的 Taint 是否能被 Pod 容忍 |
| **Pod Affinity/Anti-Affinity** | Pod 是否与节点上的其他 Pod 满足亲和/反亲和规则 |
| **PVC 绑定** | Pod 引用的 PVC 是否已绑定，且 PV 能在节点使用 |

**示例：资源不足预选**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: resource-heavy-pod
spec:
  containers:
  - name: app
    image: nginx
    resources:
      requests:
        cpu: "4"
        memory: "8Gi"
      limits:
        cpu: "4"
        memory: "8Gi"
```

如果集群中没有任何节点有 4 CPU + 8Gi 内存可用，该 Pod 将一直处于 Pending 状态。

### 9.1.3 优选（Priorities）—— 节点打分

预选通过的节点会被打分，分数范围为 0-100，Scheduler 选择得分最高的节点。

**常见的优选策略**：

| 策略 | 说明 | 权重 |
|------|------|------|
| **LeastAllocated** | 优先调度到资源空闲多的节点（分散负载） | 10 |
| **MostAllocated** | 优先调度到资源已分配多的节点（集中负载） | 10 |
| **BalancedAllocation** | 保持各节点资源分配均衡 | 10 |
| **NodeAffinity** | 根据 Node Affinity 规则打分 | 1 |
| **ImageLocality** | 节点是否已有 Pod 使用的镜像（减少拉取） | 1 |
| **PodAffinity** | Pod Affinity 软约束打分 | 1 |
| **NodeResourcesFit** | 根据资源请求与节点类型匹配打分 | 0（默认关闭）|

**LeastAllocated vs MostAllocated**：

```
假设有 3 个节点，各有 10 CPU 总量：

LeastAllocated（默认）：
  Node-A: 已用 2 CPU  → 得分高 ✓  优先选择空闲多的节点
  Node-B: 已用 6 CPU  → 得分低
  Node-C: 已用 4 CPU  → 得分中等

MostAllocated：
  Node-A: 已用 2 CPU  → 得分低
  Node-B: 已用 6 CPU  → 得分高 ✓  优先选择已分配多的节点
  Node-C: 已用 4 CPU  → 得分中等
```

### 9.1.4 抢占（Preemption）

当 Pod 优先级很高但无法调度时，Scheduler 会尝试：

1. 找到一个能容纳该 Pod 的节点
2. 如果节点资源不足，驱逐该节点上优先级更低的 Pod
3. 被驱逐的低优先级 Pod 会被重新调度到其他节点

**抢占流程**：

```
高优先级 Pod (priority=100) Pending
    │
    ▼
Scheduler 检查：
  Node-A: 资源不够，但有低优先级 Pod (priority=10)
  Node-B: 资源不够，但有低优先级 Pod (priority=20)
  Node-C: 资源足够，无需抢占 ← 优先选择
    │
    ▼
如果所有节点都需抢占：
  选择能驱逐最少 Pod 的节点
  驱逐优先级最低的 Pod
  高优先级 Pod 调度成功
```

**抢占配置示例**：

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000000
globalDefault: false
description: "高优先级 Pod，可以抢占普通 Pod"
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: normal-priority
value: 1000
globalDefault: true
description: "普通优先级，默认使用"
---
apiVersion: v1
kind: Pod
metadata:
  name: high-priority-pod
spec:
  priorityClassName: high-priority
  containers:
  - name: app
    image: nginx
    resources:
      requests:
        cpu: "2"
        memory: "4Gi"
```

## 9.2 Node 亲和性（Node Affinity）

### 9.2.1 概念

Node Affinity 让你**指定 Pod 只能调度到具有特定标签的节点**，分为硬约束和软约束。

```
硬约束（requiredDuringSchedulingIgnoredDuringExecution）：
  必须满足，否则 Pod 无法调度
  类比：租房必须"地铁附近"，不满足绝不考虑

软约束（preferredDuringSchedulingIgnoredDuringExecution）：
  优先满足，不满足也能调度
  类比：租房"朝南优先"，不朝南也可以接受
```

### 9.2.2 Node Affinity YAML 示例

**硬约束示例**（Pod 必须调度到 disk=ssd 的节点）：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: ssd-only-pod
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: disk
            operator: In
            values:
            - ssd
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 80
        preference:
          matchExpressions:
          - key: kubernetes.io/hostname
            operator: NotIn
            values:
            - node-1
  containers:
  - name: app
    image: nginx
```

**操作符说明**：

| 操作符 | 说明 |
|--------|------|
| `In` | key 的值在 values 列表中 |
| `NotIn` | key 的值不在 values 列表中 |
| `Exists` | key 存在即可，不关心值 |
| `DoesNotExist` | key 不存在 |
| `Gt` | key 的值大于指定数 |
| `Lt` | key 的值小于指定数 |

**多条件组合示例**：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: multi-condition-pod
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: disk
            operator: In
            values: ["ssd"]
          - key: memory
            operator: Gt
            values: ["16Gi"]
        - matchExpressions:
          - key: gpu
            operator: Exists
  containers:
  - name: app
    image: tensorflow/tensorflow
```

上面的配置表示：Pod 必须调度到满足以下**任一条件**的节点：
- 条件1：disk=ssd **且** memory > 16Gi
- 条件2：存在 gpu 标签

## 9.3 Pod 亲和性与反亲和性

### 9.3.1 概念

Pod Affinity/Anti-Affinity 让你**指定 Pod 之间的调度关系**：

- **Pod Affinity**：哪些 Pod 应该在同一节点（如 Web 应用与缓存在一起）
- **Pod Anti-Affinity**：哪些 Pod 不应在同一节点（如多副本防止单点故障）

```
Pod Affinity：
  Pod-A (web) ── 亲和 ──→ Pod-B (cache)  ✓ 放在同一节点，减少网络延迟

Pod Anti-Affinity：
  Pod-A (web-1) ── 反亲和 ──→ Pod-A (web-2)  ✓ 分散到不同节点，防单点故障
```

### 9.3.2 Pod Affinity 示例

**场景**：Web 应用 Pod 应与 Redis 缓存 Pod 调度到同一节点：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-app
  labels:
    app: web
spec:
  affinity:
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
          - key: app
            operator: In
            values:
            - redis
        topologyKey: kubernetes.io/hostname
    containers:
    - name: web
      image: nginx
      ports:
      - containerPort: 80
---
apiVersion: v1
kind: Pod
metadata:
  name: redis
  labels:
    app: redis
spec:
  containers:
  - name: redis
    image: redis:7
    ports:
    - containerPort: 6379
```

### 9.3.3 Pod Anti-Affinity 示例

**场景**：Web 应用的多个副本必须分散到不同节点：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - web
            topologyKey: kubernetes.io/hostname
      containers:
      - name: web
        image: nginx
        ports:
        - containerPort: 80
```

**关键参数说明**：

| 参数 | 说明 |
|------|------|
| `labelSelector` | 选择哪些 Pod 作为亲和/反亲和目标 |
| `topologyKey` | 拓扑域的标签键，`kubernetes.io/hostname` 表示以节点为拓扑域 |
| `required...` | 硬约束，必须满足 |
| `preferred...` | 软约束，优先满足 |

**topologyKey 的其他取值**：

- `kubernetes.io/hostname`：以节点为单位（最常用）
- `topology.kubernetes.io/zone`：以可用区为单位
- `topology.kubernetes.io/region`：以区域为单位

## 9.4 污点（Taint）与容忍（Toleration）

### 9.4.1 概念

Taint 是节点的"污点标记"，用于**拒绝不容忍该污点的 Pod** 调度到本节点。

```
节点 Taint：node-role=special:NoSchedule
    │
    ▼
    ├── Pod-A 有 Toleration ✓  可以调度
    ├── Pod-B 有 Toleration ✓  可以调度
    └── Pod-C 无 Toleration ✗  不能调度
```

**污点的三个效果**：

| 效果 | 说明 |
|------|------|
| `NoSchedule` | 不容忍的 Pod 不得调度到该节点 |
| `PreferNoSchedule` | 尽量避免，Scheduler 会尽量不调度，但不强制 |
| `NoExecute` | 不容忍的 Pod 会被立即驱逐（包括已在运行的） |

### 9.4.2 Taint 操作

**添加污点**：

```bash
kubectl taint nodes node-1 node-role=special:NoSchedule
kubectl taint nodes node-2 dedicated=gpu:NoSchedule
kubectl taint nodes node-3 maintenance=true:NoExecute
```

**查看节点污点**：

```bash
kubectl describe node node-1 | grep -A 10 "Taints:"
```

**移除污点**：

```bash
kubectl taint nodes node-1 node-role:NoSchedule-
```

### 9.4.3 Toleration 示例

**Pod 配置容忍**：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: tolerant-pod
spec:
  tolerations:
  - key: "node-role"
    operator: "Equal"
    value: "special"
    effect: "NoSchedule"
  - key: "dedicated"
    operator: "Exists"
    effect: "NoSchedule"
  - key: "maintenance"
    operator: "Equal"
    value: "true"
    effect: "NoExecute"
    tolerationSeconds: 60
  containers:
  - name: app
    image: nginx
```

**Toleration 关键参数**：

| 参数 | 说明 |
|------|------|
| `key` | 污点的 key |
| `operator` | `Equal`（key=value 匹配）或 `Exists`（只要 key 存在即可） |
| `value` | 污点的 value（operator 为 Equal 时指定） |
| `effect` | 污点效果：NoSchedule / PreferNoSchedule / NoExecute |
| `tolerationSeconds` | NoExecute 容忍时间，超时后 Pod 会被驱逐 |

**注意**：Toleration 是 **Pod 容忍节点**，不是节点选择 Pod。节点通过 Taint 拒绝 Pod，Pod 通过 Toleration 接受节点。

### 9.4.4 结合 Node Affinity + Taint 实现专用节点

```yaml
# Step 1: 给节点添加标签
kubectl label nodes node-1 node-role=gpu-node

# Step 2: 给节点添加污点
kubectl taint nodes node-1 node-role=gpu-node:NoSchedule

# Step 3: Pod 配置 Node Affinity + Toleration
apiVersion: v1
kind: Pod
metadata:
  name: gpu-pod
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: node-role
            operator: In
            values: ["gpu-node"]
  tolerations:
  - key: "node-role"
    operator: "Equal"
    value: "gpu-node"
    effect: "NoSchedule"
  containers:
  - name: gpu-app
    image: tensorflow/tensorflow:gpu
    resources:
      limits:
        nvidia.com/gpu: "1"
```

## 9.5 节点管理

### 9.5.1 节点状态

节点有以下状态：

| 状态 | 说明 |
|------|------|
| `Ready` | 节点正常工作，可以调度 Pod |
| `NotReady` | 节点不可用，所有 Pod 将被驱逐 |
| `SchedulingDisabled` | 节点被 cordon，禁止调度新 Pod |

### 9.5.2 Cordon —— 禁止调度

cordon 节点后，Scheduler 不会将新 Pod 调度到该节点，但已有 Pod 不会被驱逐。

```bash
# 禁止调度到 node-1
kubectl cordon node-1

# 验证
kubectl get nodes
# NAME     STATUS                     ROLES   AGE   VERSION
# node-1   Ready,SchedulingDisabled   <none>  30d   v1.28.0
```

### 9.5.3 Drain —— 驱逐 Pod

drain 节点会：
1. 先 cordon 节点（禁止新 Pod 调度）
2. 驱逐该节点上所有 Pod（DaemonSet 除外）
3. 被驱逐的 Pod 会被重新调度到其他可用节点

```bash
# 驱逐 node-1 上的所有 Pod
kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data

# 参数说明：
# --ignore-daemonsets：忽略 DaemonSet Pod（它们不应该被驱逐）
# --delete-emptydir-data：删除使用 emptyDir 的 Pod 的数据
# --force：强制驱逐，即使 Pod 没有控制器管理
```

**drain 流程**：

```
kubectl drain node-1
    │
    ├── 1. 自动执行 kubectl cordon node-1
    ├── 2. 驱逐普通 Deployment Pod → 重新调度到其他节点
    ├── 3. 驱逐 StatefulSet Pod → 重新调度
    ├── 4. 跳过 DaemonSet Pod（如 Calico、kube-proxy）
    └── 5. 驱逐完成，节点可安全维护
```

### 9.5.4 Uncordon —— 恢复调度

```bash
# 恢复调度
kubectl uncordon node-1

# 验证
kubectl get nodes
# NAME     STATUS   ROLES   AGE   VERSION
# node-1   Ready    <none>  30d   v1.28.0
```

### 9.5.5 节点维护完整流程

```bash
# 1. 查看节点状态
kubectl get nodes -o wide

# 2. 维护前：驱逐节点
kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data

# 3. 查看驱逐进度
kubectl get pods -o wide --field-selector spec.nodeName=node-1

# 4. 在节点上进行维护操作
ssh node-1
# 升级 K8s、升级内核、维护硬件等

# 5. 维护后：恢复节点
kubectl uncordon node-1

# 6. 验证节点状态
kubectl get nodes
```

## 9.6 实战1：设置 Node 标签并配置 Node Affinity

### 步骤说明

为节点添加 `disk=ssd` 标签，然后创建 Pod 通过 Node Affinity 调度到该节点。

### 完整步骤

```bash
# Step 1: 查看当前节点
kubectl get nodes

# Step 2: 给节点添加标签
kubectl label nodes node-1 disk=ssd
kubectl label nodes node-2 disk=hdd

# Step 3: 验证标签
kubectl get nodes -L disk
# NAME     STATUS   ROLES   AGE   VERSION   DISK
# node-1   Ready    <none>  30d   v1.28.0   ssd
# node-2   Ready    <none>  30d   v1.28.0   hdd

# Step 4: 创建使用 Node Affinity 的 Pod
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: ssd-pod
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: disk
            operator: In
            values: ["ssd"]
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        preference:
          matchExpressions:
          - key: kubernetes.io/hostname
            operator: In
            values: ["node-1"]
  containers:
  - name: app
    image: nginx
    ports:
    - containerPort: 80
    volumeMounts:
    - name: data
      mountPath: /data
  volumes:
  - name: data
    emptyDir: {}
EOF

# Step 5: 检查 Pod 调度位置
kubectl get pod ssd-pod -o wide
# NAME      READY   STATUS    RESTARTS   AGE   NODE
# ssd-pod   1/1     Running   0          10s   node-1

# Step 6: 清理
kubectl delete pod ssd-pod
kubectl label nodes node-1 disk-
kubectl label nodes node-2 disk-
```

## 9.7 实战2：使用 Pod Anti-Affinity 分散副本

### 步骤说明

创建一个 Deployment，通过 Pod Anti-Affinity 将副本分散到不同节点，实现高可用。

### 完整步骤

```bash
# Step 1: 创建带 Pod Anti-Affinity 的 Deployment
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: anti-affinity-web
  labels:
    app: web-anti-affinity
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-anti-affinity
  template:
    metadata:
      labels:
        app: web-anti-affinity
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - web-anti-affinity
            topologyKey: kubernetes.io/hostname
      containers:
      - name: web
        image: nginx:1.25
        ports:
        - containerPort: 80
        resources:
          requests:
            cpu: "100m"
            memory: "128Mi"
          limits:
            cpu: "500m"
            memory: "256Mi"
EOF

# Step 2: 等待所有副本调度完成
kubectl rollout status deployment anti-affinity-web

# Step 3: 检查副本分布
kubectl get pods -l app=web-anti-affinity -o wide
# NAME                              READY   STATUS    NODE
# anti-affinity-web-5d8b7c6f4c-2abc1  1/1    Running   node-1
# anti-affinity-web-5d8b7c6f4c-def34  1/1    Running   node-2
# anti-affinity-web-5d8b7c6f4c-ghi56  1/1    Running   node-3

# Step 4: 验证每个节点只有一个副本
kubectl get pods -l app=web-anti-affinity -o jsonpath='{range .items[*]}{.spec.nodeName}{"\n"}{end}' | sort | uniq -c
#    1 node-1
#    1 node-2
#    1 node-3

# Step 5: 清理
kubectl delete deployment anti-affinity-web
```

**如果节点数不足**：当副本数大于可用节点数时，`required` 硬约束会导致多余的 Pod 一直处于 Pending 状态。此时可以考虑：
- 改用 `preferred` 软约束
- 增加节点数量
- 使用 `topologySpreadConstraints`（K8s 1.16+ 推荐方式）

## 9.8 实战3：设置 Taint 并配置 Toleration

### 步骤说明

为节点设置 Taint，使其只能被特定 Pod（有对应 Toleration）调度。

### 完整步骤

```bash
# Step 1: 给节点添加 Taint
kubectl taint nodes node-2 node-role=special:NoSchedule

# Step 2: 验证 Taint
kubectl describe node node-2 | grep -A 5 "Taints:"
# Taints:             node-role=special:NoSchedule

# Step 3: 创建一个不容忍的 Pod（会调度到其他节点）
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: normal-pod
spec:
  containers:
  - name: app
    image: nginx
    resources:
      requests:
        cpu: "100m"
EOF

# Step 4: 创建一个容忍 Taint 的 Pod（会调度到 node-2）
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: tolerant-pod
spec:
  tolerations:
  - key: "node-role"
    operator: "Equal"
    value: "special"
    effect: "NoSchedule"
  containers:
  - name: app
    image: nginx
    resources:
      requests:
        cpu: "100m"
  affinity:
    nodeAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        preference:
          matchExpressions:
          - key: kubernetes.io/hostname
            operator: In
            values: ["node-2"]
EOF

# Step 5: 检查调度结果
kubectl get pods -o wide
# NAME           READY   STATUS    NODE
# normal-pod     1/1     Running   node-1        ← 不容忍，在普通节点
# tolerant-pod   1/1     Running   node-2        ← 容忍，在 tainted 节点

# Step 6: 清理
kubectl delete pod normal-pod tolerant-pod
kubectl taint nodes node-2 node-role:NoSchedule-
```

## 9.9 实战4：节点维护 —— Drain 节点升级

### 步骤说明

模拟节点维护场景：drain 节点 → 升级 → uncordon 恢复。

### 完整步骤

```bash
# Step 1: 查看初始状态
kubectl get nodes
# NAME     STATUS   ROLES   AGE   VERSION
# node-1   Ready    <none>  30d   v1.28.0
# node-2   Ready    <none>  30d   v1.28.0
# node-3   Ready    <none>  30d   v1.28.0

# Step 2: 查看 node-1 上运行的 Pod
kubectl get pods -o wide --field-selector spec.nodeName=node-1

# my-app-5d4b7c6f4c-def34   1/1    Running   node-1

# Step 3: Drain node-1（驱逐所有 Pod）
kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data
# node/node-1 already cordoned
# pod/my-app-5d4b7c6f4c-abc12 evicted
# pod/my-app-5d4b7c6f4c-def34 evicted
# node/node-1 drained

# Step 4: 查看被驱逐的 Pod 是否在其他节点恢复
kubectl get pods -o wide -l app=my-app

# Step 5: node-1 现在状态是 SchedulingDisabled

# node-2   Ready                      <none>  30d   v1.28.0

# Step 6: 模拟维护操作（升级 K8s 版本等）
ssh node-1 "apt-get update && apt-get install -y kubelet=1.29.0-*"

# Step 7: 恢复节点调度
kubectl uncordon node-1
# node/node-1 uncordoned

# Step 8: 验证节点恢复
kubectl get nodes
# NAME     STATUS   ROLES   AGE   VERSION
# node-1   Ready    <none>  31d   v1.29.0
# node-2   Ready    <none>  30d   v1.28.0
# node-3   Ready    <none>  30d   v1.28.0
```

## 9.10 实战5：使用 nodeSelector 简单限制调度

### 步骤说明

`nodeSelector` 是最简单的节点选择方式，通过 Pod 的 `spec.nodeSelector` 字段指定节点标签。

### 完整步骤

```bash
# Step 1: 给节点添加标签
kubectl label nodes node-1 environment=production
kubectl label nodes node-2 environment=staging

# Step 2: 使用 nodeSelector 创建 Pod
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: production-pod
spec:
  nodeSelector:
    environment: production
  containers:
  - name: app
    image: nginx
    resources:
      requests:
        cpu: "200m"
        memory: "256Mi"
      limits:
        cpu: "500m"
        memory: "512Mi"
EOF

# Step 3: 验证调度结果
kubectl get pod production-pod -o wide
# NAME             READY   STATUS    NODE
# production-pod   1/1     Running   node-1

# Step 4: 尝试使用不存在的标签（Pod 会 Pending）
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: pending-pod
spec:
  nodeSelector:
    environment: development
  containers:
  - name: app
    image: nginx
EOF

# Step 5: 查看 Pending 原因
kubectl describe pod pending-pod | grep -A 5 "Events:"
# Events:
#   Type     Reason            Age   From               Message
#   ----     ------            ----  ----               -------
#   Warning  FailedScheduling  10s   default-scheduler  0/3 nodes are available:
#     3 node(s) didn't match Pod's node affinity/selector.

# Step 6: 清理
kubectl delete pod production-pod pending-pod
kubectl label nodes node-1 environment-
kubectl label nodes node-2 environment-
```

**nodeSelector vs Node Affinity**：

| 特性 | nodeSelector | Node Affinity |
|------|-------------|---------------|
| 约束类型 | 仅硬约束 | 硬约束 + 软约束 |
| 匹配能力 | 简单 key=value | 支持 In、NotIn、Exists、Gt、Lt |
| 推荐度 | 简单场景 | 复杂场景 |

## 9.11 常见问题排查

### 9.11.1 Pod 一直 Pending

**排查步骤**：

```bash
# 查看 Pod 状态
kubectl get pods
# NAME      READY   STATUS    RESTARTS   AGE
# my-pod    0/1     Pending   0          5m

# 查看调度事件（最关键！）
kubectl describe pod my-pod | grep -A 20 "Events:"
```

**常见原因**：

| 事件信息 | 原因 | 解决方案 |
|----------|------|----------|
| `0/N nodes are available: N node(s) had insufficient cpu/memory` | 资源不足 | 增加节点资源或减少 Pod 请求 |
| `N node(s) didn't match Pod's node affinity/selector` | Node Affinity 不匹配 | 检查标签和 Affinity 规则 |
| `N node(s) had taint ... that the pod didn't tolerate` | Taint 未容忍 | 添加对应 Toleration 或移除 Taint |
| `N node(s) had volume node affinity conflict` | Volume 不可用 | 检查 PV/PVC 的节点亲和性 |
| `N node(s) were unschedulable` | 所有节点被 cordon | uncordon 节点 |

### 9.11.2 Node Affinity 规则不生效

```bash
# 1. 确认节点标签存在
kubectl get nodes --show-labels

# 2. 确认 Pod 的 Affinity 配置正确
kubectl get pod my-pod -o yaml | grep -A 20 affinity

# 3. 使用 describe 查看调度详情
kubectl describe pod my-pod
# 关注 Events 中的 "Predicates" 或 "FailedScheduling" 信息

# 4. 检查标签值是否匹配
kubectl get nodes -L disk
# 确认节点标签值与 Affinity 中的 values 一致
```

### 9.11.3 Pod Anti-Affinity 不分散

```bash
# 1. 确认节点数量 >= 副本数量
kubectl get nodes

# 2. 确认 topologyKey 设置正确（kubernetes.io/hostname 表示按节点分散）
kubectl get deployment my-app -o yaml | grep topologyKey

# 3. 确认 labelSelector 匹配 Pod 自身
kubectl get deployment my-app -o yaml | grep -A 5 podAntiAffinity

# 4. 节点不足时，多余 Pod 会 Pending，改用 preferred 软约束
```

### 9.11.4 Taint 无法移除

```bash
# 确认命令格式（注意 key 后面的 -）
kubectl taint nodes node-1 key:NoSchedule-
#                              ^^^^^^^^^^^^^^^ 最后的 - 表示移除

# 如果有多个 effect，需要指定完整
kubectl taint nodes node-1 key:NoExecute-

# 查看当前 Taint
kubectl describe node node-1 | grep "Taints:"
```

### 9.11.5 Drain 失败

```bash
# 常见错误：有 Pod 使用 emptyDir
# 解决：添加 --delete-emptydir-data
kubectl drain node-1 --delete-emptydir-data

# 常见错误：有未受控的 Pod
# 解决：添加 --force
kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data --force

# 常见错误：有 StatefulSet Pod 无法立即迁移
# 解决：等待或手动处理 PVC
```

### 9.11.6 调度器日志排查

```bash
# 查看 K8s Scheduler 日志
kubectl logs -n kube-system kube-scheduler-{master-node}

# 过滤调度相关日志
kubectl logs -n kube-system kube-scheduler-{master-node} | grep -i "scheduling\|bind\|predicate"

# 使用 kubectl 调试
kubectl get events --field-selector reason=FailedScheduling
```

## 9.12 章节小结

### 核心知识图谱

```
                    ┌──────────────────────────────┐
                    │      K8s 调度机制            │
                    └──────────────┬───────────────┘
                                   │
           ┌───────────────────────┼───────────────────────┐
           │                       │                       │
           ▼                       ▼                       ▼
    ┌───────────────┐      ┌───────────────┐      ┌───────────────┐
    │   预选        │      │   优选        │      │   抢占        │
    │  (过滤节点)   │      │  (节点打分)   │      │ (优先级驱逐)  │
    └───────────────┘      └───────────────┘      └───────────────┘
           │                       │                       │
           │                       │                       │
    ┌──────┴──────┐          ┌──────┴──────┐          ┌──────┴──────┐
    │资源检查     │          │LeastAllocated│          │PriorityClass│
    │端口冲突     │          │MostAllocated │          │高优先级抢占 │
    │Volume限制   │          │NodeAffinity  │          │驱逐低优先级 │
    └─────────────┘          └─────────────┘          └─────────────┘

    ┌─────────────────────────────────────────────────────────────┐
    │                    节点选择策略                              │
    ├─────────────────────────────────────────────────────────────┤
    │ nodeSelector          │ 简单 key=value 选择                │
    │ Node Affinity         │ 硬/软约束，复杂匹配                │
    │ Pod Affinity          │ Pod 间亲和调度                     │
    │ Pod Anti-Affinity     │ Pod 间反亲和调度                   │
    │ Taint/Toleration      │ 节点与 Pod 的双向选择              │
    └─────────────────────────────────────────────────────────────┘

    ┌─────────────────────────────────────────────────────────────┐
    │                    节点管理                                  │
    ├─────────────────────────────────────────────────────────────┤
    │ cordon    → 禁止新 Pod 调度到节点                           │
    │ drain     → 驱逐节点上所有 Pod                              │
    │ uncordon  → 恢复节点调度                                    │
    └─────────────────────────────────────────────────────────────┘
```

### 关键要点回顾

1. **Scheduler 三阶段**：预选（过滤）→ 优选（打分）→ 抢占（优先级）
2. **Node Affinity**：硬约束 `required` 必须满足，软约束 `preferred` 优先但可跳过
3. **Pod Anti-Affinity**：使用 `topologyKey: kubernetes.io/hostname` 将副本分散到不同节点
4. **Taint/Toleration**：节点通过 Taint "拒绝" Pod，Pod 通过 Toleration "接受" 节点
5. **节点维护流程**：cordon → drain → 维护 → uncordon
6. **排查 Pod Pending**：`kubectl describe pod` 查看 Events 中的 FailedScheduling 是第一步
